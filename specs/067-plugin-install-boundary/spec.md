# Feature Specification: 官方整合安裝邊界 — 目錄失敗隔離、收據與衝突恢復(C 批次)

**Feature Branch**: `feat/plugin-install-boundary-c`
**Created**: 2026-11-05
**Status**: Draft
**Input**: Spec 065/066 批次界線(「C:本機匯入可行性、衝突恢復與安全檢查;不覆蓋非受管檔案、不繞過信任」)、`official-agents.ts` 與其測試的現況審查(見 implementation-notes.md)。

## 決策與範圍

B 批次把官方整合的安裝入口收斂到插件頁,並刻意不動安裝邊界。審查發現安裝邊界的**基本保護已經成立**(不採用外來目錄、不覆寫被改過的檔案、回滾、稽核),C 真正需要補的是三件事,而不是「再加保護」:

1. **失敗隔離**:官方整合目錄讀取失敗,不得讓整個插件頁(含使用者插件)一起失敗。
2. **收據損毀的出路**:收據檔壞掉時,不得讓所有整合同時卡在 `error` 且無法移除。
3. **衝突的 app 內出路**:`conflict`/`error` 目前只能「開啟資料夾」;要不要、以及如何提供不破壞非受管檔案的恢復。

「本機匯入」目前沒有定義(見 implementation-notes.md 三種解讀)。本規格**建議不做**,理由與待裁決事項見下。

### 待裁決(開始實作前必須由使用者決定)

| # | 問題 | 建議 | 若不採用建議 |
| --- | --- | --- | --- |
| D1 | 「本機匯入」要做嗎?(a) 匯入使用者自己的可執行 adapter、(b) 匯入宣告式外掛資料夾、(c) 離線安裝官方套件 | **都不做**。(a) 破壞信任模型且接近已排除的發佈機制;(b) 現行「放進資料夾 + Reload」已是文件化流程;(c) 套件已隨 app 打包。在 spec 記為「不支援」並寫明理由。 | (b) 可作為獨立小功能另立 spec;(a) 需要新的安全設計,不應在本批次內完成。 |
| D2 | 收據遺失但檔案位元組與 app 套件完全相同時,可否由操作者明確「重新採用」? | **可以,但需明確操作**:保留既有 `installationId`、重建收據、不授權任何專案、稽核。僅限位元組完全相等。 | 不採用則維持 `conflict`,出路是 D3 的「移開」。 |
| D3 | `conflict`/`error` 的恢復方式 | **「移開」而非刪除**:把該目錄原子改名為 `<id>.moved-<時間戳>`(同一父目錄內),保留全部內容,操作者確認後才做,稽核;之後該整合回到 `not-installed` 可重新安裝。 | 只提供更清楚的訊息與「開啟資料夾」(現狀)。 |

## User Scenarios & Testing *(mandatory)*

| 故事 | 優先級 | 說明 |
| --- | --- | --- |
| US7 一個壞的整合目錄不拖垮插件頁 | P0 | 缺陷修復,不依賴 D1–D3 |
| US8 收據損毀時仍能處理整合 | P1 | 依 D2/D3 |
| US9 衝突時有不破壞資料的出路 | P1 | 依 D3 |

### User Story 7 — 失敗隔離(P0,已實作)

隨附套件目錄缺失,或某個套件 manifest／checksum 無效時,插件頁仍列出所有使用者插件;官方整合區塊顯示具體錯誤與重試,而不是整頁「載入失敗」。

### User Story 8 — 收據損毀(P1)

`.official-ai-installations.json` 無法解析時,操作者看到「安裝紀錄損毀」的明確原因與下一步,而不是每個整合一句相同的 `error`;下一步不得是無聲覆寫該檔。

### User Story 9 — 衝突恢復(P1)

整合目錄被判為 `conflict` 時,操作者可以在詳情看到會被怎麼處置、什麼內容保留,確認後把它移開並重新安裝;任何時候都不刪除操作者不認得的檔案。

### Edge Cases

- 隨附套件目錄存在但為空:目錄為空清單(不是錯誤)。
- 隨附套件根目錄不存在:`list()` throw;插件頁顯示目錄錯誤與重試,使用者插件照常列出。
- 單一套件無效:其他有效套件仍可列出,無效者以 `error` 列出並帶原因(而非讓整個 `list()` throw)。
- 「移開」目標名稱已存在:加序號,不覆寫。
- 「移開」時目錄是 symlink／junction:改名的是連結本身,不跟隨進入。
- 移開後 `installationId` 作廢:專案授權不沿用(與重裝同語意)。
- Windows:改名遇到檔案被占用 → 回報失敗並保持原狀,不做部分移動。

## Requirements *(mandatory)*

### Functional Requirements

#### 失敗隔離(US7)

- **FR-001** 目錄讀取以套件為單位隔離失敗:無效、checksum 不符或身分重複的套件回傳 `error` 狀態列(身分用目錄名,不遮住有效列),不讓 `list()` 整體 throw。隨附套件**根目錄**不可讀仍然 throw——那是封裝缺陷,回傳空清單會讓它看起來像「沒有整合」;由 FR-002 在 UI 層隔離。(已實作)
- **FR-002**(已實作)插件頁載入把「外掛清單」與「官方整合目錄」分開處理:任一失敗不得使另一個消失;目錄失敗時顯示具體錯誤與重試,使用者插件照常列出。
- **FR-003** 既有 `plugins:list` 與 `plugins:officialAgents` 的成功路徑回傳形狀不變。

#### 收據與恢復(US8、US9;依 D2/D3 裁決)

- **FR-010** 收據檔無法解析時,所有整合顯示同一個可辨識的原因(安裝紀錄損毀),且不因此對檔案系統做任何寫入。
- **FR-011** 移開(D3):僅在 `conflict`/`error` 且經操作者確認後執行;在同一父目錄內以原子改名完成;不刪除、不複製、不讀取其內容;結果與目標路徑回報給操作者。
- **FR-012** 重新採用(D2):僅在檔案位元組與 app 套件完全相同時提供;保留既有 `installationId`;重建收據;不改任何專案設定、不授權任何專案。
- **FR-013** 上述每個變更寫入 `config_changed` 稽核,內容與 B 的 install／uninstall 同等級(含動作、pluginId、結果)。
- **FR-014** 這些動作只能經插件頁的官方整合詳情觸發;擷取來源頁不新增任何變更入口。

#### 邊界(不做)

- **FR-020** 不支援匯入使用者自備的可執行 adapter(D1-a);第三方可執行 tailer 繼續被通用外掛系統拒絕。
- **FR-021** 不新增遠端來源、發佈或更新機制。
- **FR-022** 任何動作不得刪除操作者不認得的內容,不得繞過內容雜湊信任與同意流程。

### Key Entities

- **整合列(目錄側)**:`{ agentKind, pluginId, state, error?, installationId? }`;C 增加可辨識的錯誤類別(目錄不可用／紀錄損毀／衝突),讓 UI 不必靠比對錯誤字串。
- **安裝紀錄(收據)**:`.official-ai-installations.json`,以 `pluginId` 為鍵的 `{ installationId, manifestHash, codeHash }`。
- **移開記錄**:被改名後的目錄 `<id>.moved-<時間戳>` 與對應稽核事件。

## Success Criteria *(mandatory)*

- 隨附套件目錄缺失或含壞套件時,插件頁仍列出全部使用者插件,並顯示官方整合區塊的具體錯誤與重試。
- 收據損毀時錯誤原因明確,且無任何檔案被改動;不再有「全部 error、無法處理」的死胡同(依 D3 至少有移開出路)。
- 恢復動作之後,磁碟上原內容完整保留,可由操作者自行檢視;沒有任何專案因此自動被授權。
- 不新增可執行碼的信任路徑;第三方可執行 adapter 仍被拒絕。
- 五道 push gate 與相關 e2e(含 Windows 路徑行為的單元測試)通過。

## Assumptions

- 單實例鎖仍在;`inspect` 與變更之間的競態只可能來自操作者或外部程式,不另加跨行程鎖。
- 「移開」沿用同一父目錄,避免跨磁碟改名失敗。
- 驗收在 macOS 原生 Electron;Windows 路徑與占用行為以單元測試涵蓋,原生驗收由後續平台 gate 承接。
