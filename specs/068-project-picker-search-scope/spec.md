# Feature Specification: 專案選擇畫面 — 搜尋與範圍狀態徽章

**Feature Branch**: `feat/project-picker-search-scope-badge`
**Created**: 2026-11-05
**Status**: Draft
**Input**: 2026-11-05 提供的專案啟動介面設計稿與 `ProjectPicker.tsx`／`project-manager.ts`／`config.ts` 現況審查(見 implementation-notes.md)。

## 決策與範圍

設計稿裡值得採用的只有兩件事:**在專案清單上找專案**,以及**在列上看出這個專案有沒有宣告範圍**。建立流程不動——範圍仍由 Settings ▸ Scope 持有(#297)。

兩件事都不新增能力,只是讓既有資料讀得到:

1. 搜尋是對已載入清單的前端篩選,不新增 IPC。
2. 範圍徽章需要一個新的唯讀查詢,因為清單目前沒有範圍欄位。**這個查詢必須能說「不知道」**,否則一個損毀的 `config.yaml` 會被顯示成「未設定範圍」(見 implementation-notes 陷阱 1、2)。

### 待裁決

| # | 問題 | 建議 |
| --- | --- | --- |
| D1 | 搜尋框何時顯示 | 專案數 ≥ 6 才顯示。少於此數時多一個輸入框只是雜訊;首次使用者看到的是乾淨的清單。 |
| D2 | 已設定範圍要不要也顯示徽章(「N 個目標」) | 顯示,但用中性樣式;只有「未設定」用提示色。設計稿也是兩者都有。若認為雜訊太多,可只顯示「未設定」。 |
| D3 | 搜尋框內按 Enter | 只有恰好一個符合時才開啟該專案;多個符合時把焦點移到第一列。避免「看起來選的是 A、實際開了 B」。設計稿是直接開第一項。 |
| D4 | 徽章讀取的時機 | 清單先顯示,徽章另一次非同步讀取補上(失敗則不顯示徽章)。不併進 `project:list`,以免範圍讀取拖慢或拖垮清單。 |

## User Scenarios & Testing *(mandatory)*

| 故事 | 優先級 | 說明 |
| --- | --- | --- |
| US1 在清單上用名稱找專案 | P1 | 前端篩選,不動資料層 |
| US2 在清單上看出哪個專案還沒宣告範圍 | P1 | 新的唯讀範圍摘要,三態 |

### User Story 1 — 搜尋(P1)

專案多了之後,操作者輸入名稱片段就能把清單縮到符合者;清空即回到完整清單。篩選不改變排序、不影響改名／刪除／開啟。

### User Story 2 — 範圍狀態(P1)

操作者在清單上就能看出每個專案是「已宣告 N 個目標」、「未宣告範圍」,或「讀不到範圍(狀態未知)」,不必逐一開啟專案。「未宣告」是提示而不是警報——剛建立的專案本來就還沒有範圍。

### Edge Cases

- 篩選結果為 0:顯示「沒有符合『…』的專案」與清除篩選,**與「還沒有任何專案」的空狀態不同文案**。
- 清單載入失敗:沿用既有失敗狀態,不顯示搜尋框(沒有可搜尋的資料)。
- 篩選中刪除了最後一個符合的專案:回到「沒有符合」狀態,不自動清掉搜尋字串。
- 篩選中改名使其不再符合:該列留到提交完成再消失,不在輸入途中跳走。
- 同名專案(已有的「同名多顯示建立日期」)篩選後仍保持區分。
- 範圍摘要查詢整體失敗:所有徽章都不顯示(不是顯示成「未設定」)。
- 單一專案的 `config.yaml` 損毀:只有那一列顯示「狀態未知」。
- 專案只用 scope 檔(Burp／ZAP)宣告範圍:計入條目數,不判為未設定。
- scope 檔讀不到或格式無效:該列「狀態未知」,不是「未設定」。
- 專案目錄剛建立、`config.yaml` 尚不存在:「未宣告」(合法的新專案)。

## Requirements *(mandatory)*

### Functional Requirements

#### 搜尋(US1)

- **FR-001** 專案數達門檻(D1)時,清單上方顯示搜尋框與「符合數／總數」;未達門檻不顯示。
- **FR-002** 以名稱做不分大小寫、以空白分詞的 AND 比對;沿用現有共用的比對函式,不複製第三份。篩選只影響顯示,不改變資料、排序或選取行為。
- **FR-003** 篩選結果為 0 與清單為空是兩個不同狀態,各有自己的文案;前者提供「清除篩選」。
- **FR-004** 搜尋框內的方向鍵與輸入不得觸發列表開啟或導覽;Enter 依 D3。既有的鍵盤開啟、建立欄位焦點行為不退化。
- **FR-005** 搜尋框有可存取名稱;篩選結果數變化以 `role="status"` 告知。

#### 範圍狀態(US2)

- **FR-010** 新增唯讀查詢,對清單中每個專案回傳範圍摘要,三態:`{ state: 'set', count }`、`{ state: 'unset' }`、`{ state: 'unknown', reason }`。`count` 為實際生效的範圍(`scope.targets` 與 scope 檔條目合併去重)。
- **FR-011** `unknown` 的條件:`config.yaml` 存在但無法讀取或解析;scope 檔已指定但 `unreadable`／`invalid`。`config.yaml` 不存在視為 `unset`。**不得**透過會吞錯誤的 `loadConfig` 取得此判斷。
- **FR-012** 該查詢不寫入任何檔案、不改變 `lastOpened`、不開啟專案資料庫。
- **FR-013** 單一專案的失敗只影響那一列;查詢整體失敗時清單照常顯示、不顯示徽章,且不把失敗呈現為「未設定」。
- **FR-014** 徽章語氣沿用 `scopeIssue`:`unset` 是提示層級(不使用警報色、不使用「警告」字樣);`unknown` 為中性的「狀態未知」,可帶原因於 `title`。
- **FR-015** 徽章文案走 i18n(en／zh-TW),計數使用單複數安全的寫法,不寫死「規則」字樣(範圍條目是目標,不是規則)。
- **FR-016** 範圍摘要不改變 `ProjectMeta` 的既有欄位,也不改 `project:list` 的回傳形狀(D4)。

### Key Entities

- **範圍摘要**:`{ projectId, state: 'set' | 'unset' | 'unknown', count?, reason? }`,每次進入選擇畫面讀取一次,僅供顯示。
- **清單篩選**:元件內的字串狀態,不持久化。

## Success Criteria *(mandatory)*

- 10 個以上專案時,輸入名稱片段能在不捲動的情況下找到目標;清空後完整清單回復。
- 一個 `config.yaml` 損毀的專案顯示「狀態未知」,**不是**「未宣告範圍」;只用 scope 檔宣告範圍的專案不被標成未宣告。
- 範圍摘要讀取失敗時,清單的載入、開啟、改名、刪除都不受影響。
- 清單載入時間不因範圍摘要變慢(徽章晚於清單出現是可接受的)。
- 既有的專案清單 e2e、鍵盤開啟、載入／空／失敗狀態回歸全綠;五道 push gate 通過。

## Assumptions

- 專案數量為數十個以內;不做分頁或虛擬捲動。
- 範圍摘要在進入選擇畫面時讀取一次,不輪詢;使用者在別處改了範圍,下次進入畫面才會更新。
- 不改建立流程、不新增「開啟本機專案」入口(與本規格無關)。
- 驗收在 macOS 原生 Electron;Windows 路徑與檔案鎖行為以單元測試涵蓋。
