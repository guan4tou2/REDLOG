## 1. 過深的 `data`：寫入端限制深度

### 問題

兩個 verifier 重算雜湊時都遞迴走列的 `data`。`tools/redlog-verify.py`（隨 bundle 交給客戶的那一個）會在 Python 的遞迴上限停下：`data` 巢狀超過約 332 層陣列（Python 3.9、3.11；3.12 以上約 497 層）的列，在那裡被報成 **CHAIN BROKEN**，雖然列完好無損。能送 `data` 的來源——交接檔、AI 工具的輸入、代理解析出的 JSON 請求本體——自己決定它有多深，所以一筆真實的擷取可以在客戶執行的 verifier 中看起來像被竄改過。

實測（2026-11-14，本機，變更前）：寫入端收下 `data` 至 1,000 層（超過時 FTS 的 `json_tree` 失敗，整列不寫入）；app 自己的 verifier 約在 2,300 層失敗；`POST /api/events` 在解析前以 400 拒絕超過 64 層的請求本體（9aa28ed3；即 `data` 超過 63 層，見 §2）。數字與版本見 [Spec 071 plan D13](../../../specs/071-event-provenance-and-ingestion-contract/plan.md)。

### 考慮過的三個做法

| 做法 | 內容 |
|---|---|
| verifier 回報「此處無法檢查」 | 過深的列不判為斷鏈，改報無法驗證；verifier 要改，已出貨的 bundle 內附的 verifier 不會變 |
| 寫入端限制深度 | 寫入時就不讓 `data` 深到任何 verifier 走不動 |
| 調高遞迴上限 | Python verifier 執行時調高 `sys.setrecursionlimit`；上限與 C 堆疊相依，調太高會換成直譯器當掉 |

### 擁有者的決定

「寫入端限制深度」

### 實作者的解讀（不是擁有者的話）

| 項目 | 解讀 | 理由 |
|---|---|---|
| 怎麼限制 | **無損、可自行還原的折疊**：第 63 層以內原樣；第 64 層含容器或為標記形狀的容器，換成 `{"_collapsed": "<其 JSON 文字>"}`（與 `JSON.stringify` 逐位元組相同）；來源自己在第 64 層的標記形狀物件也包起來，所以第 64 層的標記形狀物件全是寫入端做的，`restoreDataDepth` 只憑存入的列還原；`_ingest.collapsed` 記數目 | 拒收或截斷會遺失證據，違反 2026-11-13 §12 的完整擷取。第一版把容器換成裸字串、只記數目，經獨立審查證明讀者分不出包裝與來源送來的 JSON 字串（`["[1]",[1]]` 與 `[[1],"[1]"]` 存成同樣的位元組），因此改為包裝物件 |
| 上限 | **64**（`data` 本身為第 1 層，純量不計層） | repo 內 fixture 最深 3 層；本機 323,816 筆 AI 工具呼叫的輸入最深 5 層；Python verifier 最不利的形狀在 332 層失敗，約 5 倍餘裕。API 原本的 64 層計的是請求本體，對 `data` 而言是 63 層，不是同一個數 |
| 已寫入的列 | **不遷移、不改寫** | 產品未發行，不做相容（Spec 077 R8） |
| 兩個 verifier | 不改 | 受限後的列對兩者都在上限內；以新的共用向量 `test/fixtures/depth-vectors` 證明 |

規格：[Spec 071](../../../specs/071-event-provenance-and-ingestion-contract/spec.md) FR-097、FR-005 的 `collapsed` 列、FR-006 的註記；plan D13；tasks T03A。

## 2. API 入口不再以深度拒絕事件

### 問題

`POST /api/events` 在解析之前就以 400 拒絕巢狀超過 64 層的請求本體（即 `data` 超過 63 層；9aa28ed3 為防遞迴走訪溢位而加的、所有 JSON 路由共用的閘門）。這個 400 在伺服器端無聲：沒有 log、沒有 capture-health 註記、沒有缺口列。mitm addon 收到 4xx 既不寫交接檔也不記錄，而它正是會送出由目標或測試者決定的巢狀 JSON（解析後的 HTTP 請求本體）的來源，所以那筆觀察就此遺失；同一個項目經交接目錄則以折疊形式保存。

### 考慮過的兩個做法

| 做法 | 內容 |
|---|---|
| 收下並摺疊 | 事件路由不以深度拒絕，交給寫入端的界限 |
| 維持拒絕並寫缺口列 | 仍回 400，但寫一列缺口，記下有項目因深度被拒 |

### 擁有者的決定

「收下並摺疊」

### 實作者的解讀（不是擁有者的話）

| 項目 | 解讀 |
|---|---|
| 範圍 | 只有事件路由（`POST /api/events`，與共用 handler 的 `/api/events/seed`；Phase 5 的 `/api/ingest` 寫在規格中）不再以深度拒絕；其他 JSON 路由（標記、書籤、設定、錄製、loot 掃描等）的 64 層閘門照舊，因為它們遞迴走自己的本體，也不是證據擷取 |
| 請求本體的大小上限 | 20 MiB 不變 |
| 變更之後仍會遺失過深觀察的地方 | mitm addon 自己的 `json.loads`（Python 3.9 約 1,000 層 `RecursionError`，`_extract_params` 接不到；未對 mitmproxy 內附的 Python 驗證）；AI 工具輸入超過 100 KiB 時只存鍵名；Codex adapter 的 `JSON.stringify(payload.output)` 在 Node 約 6,100 層失敗並被吞掉；收到非 2xx 就丟棄的來源（`c2-tailers/follow.js`、`pcap-capture.js`、`redlog-relay.py`）。皆未在本次修改 |

### 後續：十萬層的上限（同日）

**問題**：「收下並摺疊」之後，事件路由在解析前不再看深度。解析與折疊不遞迴，但每一層仍佔記憶體；請求本體的 20 MiB 上限容得下約一千萬層，交接檔沒有大小上限。

**擁有者被問到的問題**：「事件 API 超過十萬層就拒絕並記缺口，可以嗎？」

**擁有者的回答**：「可以」

**實作者的解讀（不是擁有者的話）**：

| 項目 | 解讀 | 理由 |
|---|---|---|
| 怎麼數 | 整個請求本體或交接檔的層數（根為第 1 層），在解析之前以線性掃描計算（`jsonDepthExceeds`）；超過 100,000 層才拒絕，恰好 100,000 層照常收下並摺疊 | 在解析前就決定，被拒的本體不佔解析的記憶體 |
| API 的回應 | `413`，本體 `{"error": "...", "reason": "nested-too-deep"}` | 讓來源看得到原因 |
| 交接檔 | 套用同一個上限：不解析，移入隔離區（`nested-too-deep`），計入該次排空的缺口列 | 兩個入口對同一個項目做同一件事；擁有者的問題只問到 API |
| API 的缺口列 | `system`／`capture_gap`：`source: "api"`、`door: "legacy-api"`、`reason: "nested-too-deep"`、`intentional`、`skipped_units`、`bytes`、`max_nesting: 100000`、`gap_started_at`、`gap_ended_at`、`description`；不含被拒項目的任何內容 | 與交接檔的缺口列同形；內容沒有被保存，所以列上沒有 |
| 合併 | 每個開著的專案：第一次拒絕立刻寫一列並開一個 60 秒的視窗；視窗內的拒絕在視窗結束時寫成一列，並開下一個視窗；沒有拒絕的視窗結束這一串。持續的來源是開頭一列、其後每分鐘一列。專案關閉、切換或程式結束前先寫出開著的視窗（`stopProject`）；只有行程未經 `stopProject` 就結束時，開著的視窗的計數遺失。交接檔一次排空的同一原因合成一列（既有規則） | 一個卡在迴圈裡的來源一分鐘寫一列，不是每個請求一列 |
| 暫停時 | 寫 `intentional: true`，匯出不計為遺失（交接檔的慣例：暫停時的項目本來就不會被記錄）；標記例外，但未解析的本體看不出種類 | 擁有者沒有被問到這一點 |
| 為什麼是十萬 | 本機實測（Node 24.12）：十萬層的本體解析約 11 ms、折疊約 13 ms、RSS 約 +19–27 MB；層數再往上，記憶體隨層數線性增加，一千萬層的交接檔解析本身尖峰已約 1.2–1.7 GB，可能使行程記憶體不足而中止 | 十萬層遠高於任何觀察到的正當來源（最深 6 層），又遠低於會耗盡記憶體的深度 |

規格：Spec 071 FR-097 的「上限之外」；plan D13 的「十萬層的上限」。

## 3. 代理不再送出解析後的 JSON 請求本體

### 問題

§1 的深度來源之一是 HTTP 代理 addon 的 `params.body_json`：請求本體是 JSON 時，addon 把它解析後的整棵樹放進事件。這是唯一一個由目標或測試者決定巢狀深度的欄位。同一份內容事件裡已有原文（`request_body`，大的移到 sidecar）與預覽；`src/` 沒有任何程式讀 `body_json`；匯出的範圍遮罩也不遮它。

### 擁有者的話

擁有者先問：「為何會這麼多層 其他工具都怎麼處理」

實作者的回答（摘述）：真實資料沒有這麼深，深的是測試者自己的巢狀探測或想讓擷取看起來被竄改的來源；Burp、mitmproxy 這類流量記錄工具只保存原始本體，顯示時才解析。

擁有者的決定：「拿掉」

實作者接著指出：拿掉之後，原本靠這份解析樹才搜得到的內容（JSON 編碼器寫成 `\uXXXX` 的非 ASCII 字、宣告為非 UTF-8 字元集的本體、本體的字與 URL 的字一起查）會搜不到。擁有者的決定：「移除並補搜尋」

### 實作者的解讀（不是擁有者的話）

| 項目 | 解讀 | 理由 |
|---|---|---|
| 移除什麼 | 只有 `params.body_json`。`params` 的其他欄位（`query`、`body_form`、`body_multipart`、`body_raw`）不動 | 擁有者被問到的只有這一個欄位；其他欄位同樣是本體或 URL 的複本，列為待擁有者決定 |
| 已寫入的列 | 不遷移、不改寫 | 同 §1 |
| 「補搜尋」的範圍 | 移除前搜得到的，移除後都要搜得到；順帶讓回應本體也適用同樣的規則 | 回應本體原本就沒有解析樹，同一段索引程式處理兩者 |
| 怎麼補 | 索引時把 `\uXXXX` 還原成字元另存一份文件、依事件宣告的字元集解碼文字類本體、多個字的查詢改為「每個字出現在事件的欄位或任一本體即可」 | 不解析 JSON、不改已存的列與 sidecar |

實作：PR #779。成本與已知限制寫在該 PR 與 `docs/domain/SPEC-search-query-semantics.md`。

## 4. 範圍外的列：標頭、cookie、參數在匯出時遮掉

### 問題

匯出時開啟「遮罩範圍外」，範圍外的列只有本體被換成標記；同一份內容仍從同一列的其他欄位原樣出去（`params` 裡解析過的表單、`Authorization` 與 cookie 的值、URL 的 query）。以真實的匯出函式確認：JSON、NDJSON、時間軸匯出、bundle 都如此；HAR 帶出 URL query、`Authorization`、`Cookie`。

### 擁有者被問到的事（實作者摘述，不是原文）

這個洞要現在補，還是等 Spec 077 的交付引擎。

### 擁有者的決定

「現在遮掉」

### 實作者的解讀（不是擁有者的話）

| 項目 | 解讀 | 理由 |
|---|---|---|
| 何時遮 | 只在匯出時；已存的列與雜湊鏈不動 | 既有的範圍遮罩就是匯出時的 |
| 遮哪些列 | 範圍外與未分類的列；範圍內的列不遮 | 既有遮罩的對象，沒有擴大 |
| 遮哪些欄位 | `params` 整個；標頭與 cookie 的值（名稱留下）；URL 的 query 值、userinfo、fragment；衍生列上引用這些內容的欄位。清單在 `src/core/scope-sanitize.ts` | 留下主機、路徑、名稱，交付對象仍看得出發生了什麼 |
| 形式 | **列舉式**：沒被點名的欄位原樣匯出 | 沿用既有模組的做法；逐欄位分類的 ratchet 沒有做 |
| HAR | 一律遮罩，匯出面照實說 | HAR 原本就一律遮罩，但對話框、預覽與 manifest 都說沒有 |
| 與 Spec 077 的關係 | 過渡。Spec 077 Phase 1 以「範圍外預設不交付」取代這個開關（077 tasks 的刪除清單） | — |

實作：PR #778（已合併）。仍會原樣出去的項目列在該 PR：路徑片段中的 token、標頭／cookie／參數的名稱、非 `://` 形式的 userinfo、`tls.*`、DNS 查詢名稱。

## 5. 指令的遮蔽與機密偵測歸 Spec 077

### 問題

§4 沒有遮指令文字（`command`、`argv`、loot 的 `source`、`scope_violation.action` 的指令形式）。範圍外主機的密碼可以寫在指令列上。另外，RedLog 現有的機密偵測只認得兩種東西：高熵字串（至少 20 字元、每字元至少 4.5 bit）與 denylist（含本專案 loot 的值）；`-p Passw0rd!` 這種短密碼不會被認出來。

### 擁有者的話

關於指令：「指令只需要在輸出時遮蔽就好吧」

關於偵測認不得的形式，擁有者選了實作者列出的一個選項。選項的文字是實作者寫的：「之後擴充 RedLog 本身的機密偵測，讓它認得更多形式。這屬於 Spec 077 的範圍，匯出遮罩會自動受益。」

之後擁有者再說：「指令遮蔽要併入 Spec 077」

### 實作者的解讀（不是擁有者的話）

| 項目 | 解讀 | 理由 |

| 每種工具的旗標表 | 沒有決定。FR-050 現有的指令列規則只有通用形式 | 擁有者沒有被問到；規則集要認得哪些工具，留給 077 的 plan |
