# 2026-11-16 的決定

> **寫於**：`main@19e7e4aa`。
> 擁有者的話與實作者的解讀分開列。這份紀錄記下方向，不排時程；兩件事都還沒有規格，也還沒有開始做。

## 1. 工具輸出的結構化可以內建，只記工具回報的事實；ATT&CK 技術標記走外掛

### 問題

擁有者要實作者比較 Dradis、PlexTrac、AttackForge、Faraday、PwnDoc、Reconmap 與 RedLog 的差異，以及有哪些可以參考。實作者回報：這六個產品管的是發現與報告，在 RedLog 的下游；可以參考的集中在四處，其中兩處是工具輸出的結構化與 ATT&CK 技術標記。

### 擁有者的話

> 工具輸出的結構化 可以作為內建功能
> ATT&CK 技術標記 可以作為外掛

實作者對照程式後回報：第一句與既有的一條界線相反（見下）。實作者提議把界線改畫在「事實」與「判斷」之間，問「結構化只記工具回報的事實（主機、port、服務），不做判斷（嚴重度、弱點），這條線可以嗎？」擁有者答：

> 可以，只記事實

（「可以，只記事實」是實作者寫的選項文字。）

### 它改變了哪一條既有的界線

[DESIGN-core-and-capture](../../design/DESIGN-core-and-capture.md) §2.4 的決定是「錄影全文可搜尋、保留工具自己的輸出檔，**不做解析器**」，理由是把 nmap 的 XML 讀成結構化的發現屬於解讀，什麼算發現各家不同。`src/core/cast-index.ts` 的檔頭有同一段話。

這次的決定把那條線從「不解析」移到「不判斷」：

| | 以前 | 現在 |
|---|---|---|
| 「哪幾次執行提到 445」 | 做（全文搜尋） | 做 |
| 「這次 nmap 回報了哪些主機、哪些 port、什麼狀態、什麼服務」 | 不做 | 可以內建 |
| 「這是不是弱點、多嚴重、怎麼修」 | 不做 | 不做 |

第三列沒有變。它與既有的決定一致：RedLog 不產生報告、不管理發現（[PRODUCT-POSITIONING](../../PRODUCT-POSITIONING.md)「What RedLog is NOT」）。

### 實作者的解讀（不是擁有者的話）

| 解讀 | 理由 |
|---|---|
| 「事實」是工具自己回報的內容，照它回報的樣子記下：主機、port、協定、狀態、服務名稱與版本字串。RedLog 不替它加上嚴重度、弱點名稱、修復建議或任何評分 | 擁有者確認的選項文字 |
| 解析出來的內容是對輸出的一種讀法，不是第一手擷取。依 [DESIGN-PRINCIPLES](../../design/DESIGN-PRINCIPLES.md) §3，它要標明是解析來的、能指出是哪個解析器的哪一版讀的，不能當成權威事實 | §3 既有的原則：只有操作者的標記與第一手擷取是權威 |
| 「內建」指功能在核心裡、不需要安裝外掛；不代表第一版要涵蓋很多工具 | 擁有者的用詞；沒有談到範圍 |

### 實作者的建議（擁有者沒有就這些表示意見）

這些是做的時候要先決定的事，列在這裡是為了不要重查，不是已經決定：

- **結果要能重算，不進雜湊鏈。** 解析器會出錯、會改版；寫成鏈上的列，錯誤就永久留著。原始輸出與工具自己的輸出檔才是證據，結構化的結果是可以整份刪掉重建的投影（與全文索引同一種東西）。
- **解析出來的內容不能用來做目標歸屬或範圍判定。** 輸出的內容是對方可以影響的（服務的 banner 是對方給的）；這條規則在入口已經有，結構化之後更容易被誤用。只用於顯示與搜尋。
- **優先讀工具自己的報告檔，其次才是畫面輸出。** 畫面輸出會被截斷、格式隨版本變；`file-watcher` 已經保留 `-oX` 這類輸出檔與它的 SHA-256。輸出被截斷時，結果要標明不完整。
- **解析失敗不影響原始列。**
- **第一版只做 nmap。** 擁有者的 HTTP 流量走 Burp，網頁列舉類工具的優先度低。
- **每個事實連回產生它的那一列與時間**，同一個 port 在兩次掃描之間的變化可以查。這是這六個產品都做不到的地方。

### ATT&CK 技術標記：與既有設計一致，但寫進去之後沒有讀者

擁有者的第二句話與現況一致：[PRODUCT-POSITIONING](../../PRODUCT-POSITIONING.md) 把內建的 ATT&CK 標記列為非目標、指向 `commandTags` 外掛；核心有登記表（`src/core/command-tagger.ts`，保留欄位 `mitre_ttp`、`technique_tool`、`technique_category`），刻意不內建任何樣式。

實作者查到的現況：

- 畫面、搜尋、匯出都沒有讀 `mitre_ttp`。外掛蓋上標記之後，它只存在於列的資料裡，看不到也搜不到。
- 標記在算雜湊之前寫進資料，沒有記下是哪個外掛的哪條規則蓋的；規則改版後，舊列上的標記無從追溯。蓋章裡為這件事準備的欄位（`_ingest.rules`）還沒有接上。
- 目前沒有任何內附或官方的外掛提供樣式。

做這個外掛時還要決定、擁有者沒有表示意見的：標記要在哪裡看得到與搜得到（這是核心的事，外掛不能有畫面）；操作者能不能手動替標記或指令補上技術編號；要不要有匯出成 ATT&CK Navigator layer 的匯出外掛。

### 這次比較中不參考的

報告範本與產生、附修復建議的弱點資料庫、複測、客戶入口、開票整合、多人伺服器與權限、風險評分、測試清單與方法論、以 AI 撰寫發現。前七項是既有的決定；後兩項是實作者的建議，擁有者沒有反對。
