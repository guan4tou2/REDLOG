### 3.1 #326：WSL 舊目錄遮蔽 Windows profile

唯一的「無聲丟證據」等級缺陷：hook 顯示 active、指令照常執行，事件卻 spool 到沒有人 drain 的目錄。

| | v0.18.3 | v0.18.4 |
| --- | --- | --- |
| `_redlog_resolve_dir` 探測端點 | `/api/health`（第 31 行） | `/api/whoami`（第 43 行） |
| 判定依據 | port 有回應即採用 native 目錄 | token 被接受才採用 |
| mirrored networking 下 | 該 port 就是 Windows App，health 一律 200 → 採用舊目錄 → 事件全丟 | health 不再作準；401 判定 token 過期 → fall through |

程式碼行為（`hooks/shell-common.sh`）：`200|503` 保留 `$HOME/.redlog`，其餘（含 401、連不上）落到 Windows profile。

有測試：`test/shell-wsl-directory.test.ts` 的 `stale-token` 變體，對真實本機 HTTP server 驗證「port 有回應但拒絕舊 token」不會被採用。

### 3.2 #345：Git Bash 的 payload 路徑

| | v0.18.3 | v0.18.4 |
| --- | --- | --- |
| payload 傳遞 | `--data-binary @"$work/payload.json"` | `--data-binary @-` 搭配 `< "$work/payload.json"` |
| 誰開檔 | 原生 Windows curl 解析 MSYS 路徑 | bash 先開檔，curl 只讀 stdin |
| `MSYS_NO_PATHCONV=1` | 路徑不轉換，curl 找不到 `@/tmp/...` → 走 spool（21–30 秒延遲） | 路徑不進 argv，成因消失 |
| argv | 路徑在 argv | body 在 stdin，128 KiB 上限不適用 |

注意：實際寫法是 `@-`（讀 stdin）加 shell 重定向，不是 `@//-/`。

## 5. 端到端流程

全部用真實執行的程式產生資料，不以注入 Events 代替。

**A — Kali 滲透測試**
安裝 deb → 接入 Zsh → 執行一般與失敗指令 → 驗證輸出與 exit → HTTP 工具 → Activity 定位 → 匯出證據 → 重啟後讀回。

**B — Windows 滲透測試**
安裝 → PowerShell 接入 → WSL Kali 接入 → Git Bash 接入（#345）→ 執行命令 → 檢查配對與輸出 → 匯出 → 升級 → 卸載 → 確認 PowerShell profile 與各發行版 rc 已清理。

**C — macOS 資安研究**
安裝 dmg → 接入外部 Zsh → 啟用 HTTP 擷取 → Claude Code／Codex 各兩個 Session → 查看 AI 與 Shell 記錄 → 選取 Evidence Fragment → 輸出證據包。

**D — WSL 來源選擇（#326）**

四種 native 狀態必須分開驗，對應 `test/shell-wsl-directory.test.ts` 的 `down`／`live`／`stale-token` 分法：

| 測試 | WSL native 狀態 | 預期 |
| --- | --- | --- |
| D1 | port 不可達 | 回退 Windows profile |
| **D2** | Health 200，但 Whoami 401 | **回退 Windows profile** |
| D3 | Native token 有效 | 保留 WSL native 來源 |
| D4 | Whoami 503，沒有開啟專案 | 維持目前目錄選擇，不宣稱已驗證 token |

**D2 是 #326 的主要驗收案例。** D1 只能證明「來源消失會回退」，照不到 mirrored networking 的核心情境：port 有服務回應、health 200、token 已失效。實機重現方式是在發行版內留下舊 `api-token`／`api-port`，讓 Windows App 在該 port 回應但拒絕舊 token。

**D4 的限制必須寫進驗收記錄**：`src/core/api-server.ts` 的順序是 `if (!projectOpen) → 503` 先於 `authenticate() → 401`。所以 App 開著但沒開專案時，過期 token 拿到的是 503 而非 401，token 無法判定，程式碼刻意保留舊目錄。此情境下的過期 token 風險**未完全排除**，不能記為已驗證。

## 8. 結論

v0.18.4 的方向正確：Capture → Search → Read → Select → Export → Verify 已經成形。

「擷取端不可靠」這個描述過於籠統。更準確的判斷是：

> **REDLOG 已修復多個重要的擷取可靠性問題，但修復交付、原生平台驗收、Issue 狀態與版本文件尚未同步。**

這是不同性質的問題。一方面 #326 與 #345 有具體程式碼修復，不能視為未處理的缺陷；另一方面單元與整合測試通過，不等於 v0.18.4 安裝包在原生情境下已驗證。對一個以證據完整性為核心價值的工具，驗收不能只看資料有沒有進資料庫，還要確認來源身分、指令配對、保存完整性，以及失敗時的可觀測性。

現階段最有價值的工作不是增加功能，而是讓 v0.18.4 成為「每項核心擷取能力都有明確驗證結果、失敗邊界與文件對應」的可靠基準版本。
