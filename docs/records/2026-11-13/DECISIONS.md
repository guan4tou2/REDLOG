## 1. 判斷功能的原則

以資深滲透測試者的角度判斷每個功能：這個人已經有自己的終端機、代理、瀏覽器與筆記方式，

## 10. 設定檔只含範圍（同日晚間）

擁有者裁定：匯出的設定檔只帶這個專案的範圍，也就是目標清單與排除清單；不再帶 `network.whitelist`（操作員自己的 VPS 出口）、`network.blacklist`（操作員自己的固定 IP）與 `scope.warnOnViolation`。

理由：設定檔的用途是交給隊友，而事件 JSON 匯出早已拒絕帶這兩份 IP 清單，因為它們屬於操作員、不屬於這次任務（`src/core/export-config.ts`）。兩種匯出的說法不一致，以事件 JSON 匯出為準。

讀取也跟著收緊：匯入時 `version` 必須恰好是 `1`；出現未定義的欄位（頂層或 `scope` 底下）就整份拒絕並列出欄位名稱，不再悄悄忽略；舊格式的檔案（含 `network:`）因此會被拒絕。產品尚未發行，不做相容、不做遷移。匯入新專案時，網路清單與範圍外警告維持預設值。

不在這次範圍：匯入到既有專案、匯入前的差異預覽、把匯出控制移到目標頁。

### 三個階段

| 階段 | 做什麼 | 不做什麼 |
|---|---|---|
| 擷取 | 保存已啟用來源送來的全部事件 | 不以範圍過濾 |
| 審閱 | 判定目標、歸屬、私人內容與範圍狀態；允許未知與事後修正 | 不修改原始事件 |
| 交付 | 依當下的政策選取、遮蔽並輸出；唯一的交付判斷點 | — |

「完整擷取」指已啟用的擷取來源所觀測到的內容，不是預設監控整台電腦，也不繞過明確的暫停或私人資料保護設定。
範圍外不等於無關，也不等於私人：`whoami`、`ip route`、DNS 查詢、建立代理連線可能沒有明確的範圍目標，卻是證據。
交付的判定是三值的（納入、排除、待確認）；待確認不得默默當成排除，也不得默默當成納入。

### 五條不變條件（要寫進 Spec 077）

1. **範圍不控制擷取。** 已啟用來源的事件不得僅因超出範圍而被拒收、丟棄或截斷。
2. **範圍不修改原始證據。** 修改範圍只更新分類或交付判斷。
3. **未知不是安全，也不是範圍外。** 未知的事件不得被默默歸入某個確定的分類。
4. **交付政策集中執行。** 介面預覽、CLI、API、bundle、HAR 等輸出路徑使用同一個判斷，並保留政策版本與結果。
5. **完整性與交付範圍分離。** 被排除的事件不使原始證據鏈失效；交付產物要能驗證其內容與選取政策。只交付部分事件的 bundle 必須有可驗證的選取證明，或明確標示為經過篩選的衍生交付物，不得宣稱為完整的原始鏈。

### 範圍的歷史

修改範圍可以重新判定，但不重新定義事件發生時的事實。要能分開回答四件事：當時做了什麼；事件發生時適用的範圍；現在的範圍；交付判斷用了哪一個範圍版本與哪些人工決定。
14:00 掃描某主機、14:30 客戶才把該網段加入範圍，不代表 14:00 的操作當時已獲授權。
一般交付以目前選定的範圍重新評估事件，同時保留歷史版本與變更時間；涉及授權合規時，要能查事件發生當時的授權狀態。
