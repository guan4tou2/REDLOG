# 工具輸出的事實與技術標記：實作與設計分析

> **狀態**：research — 設計分析，不是需求。兩個方向由擁有者於 2026-11-16 定下（[DECISIONS](../records/2026-11-16/DECISIONS.md) §1）；要做時先開規格，本頁是開規格前的材料
> **依據**：`main@f59ed853` 的程式（唯讀）。標「未量測」「未驗證」者沒有執行過
> **相關**：產品比較見 [Topic E](PRIOR-ART-E-pentest-platforms-and-operator-tools.md)

擁有者的三句話：工具輸出的結構化可以作為內建功能；ATT&CK 技術標記可以作為外掛；結構化只記工具回報的事實，不做判斷。本頁回答怎麼做，並把做之前要擁有者決定的事逐項列出（§5）。

## 0. 摘要

1. 兩件事是同一種東西：**對已存的原始紀錄的一種讀法**。讀法會出錯、會改版，所以結果要能整份刪掉重算，不進雜湊鏈；原始輸出才是證據。這與全文索引（`cast-index`、body 索引）和 Spec 074 的投影是同一類。
2. **結構化可以分三期，第一期不需要任何新的儲存**：把解析器做成純函式，事件詳情開啟時就地解析那一筆的輸出。跨指令的查詢（目標頁的服務清單、搜尋條件）才需要投影，等 Spec 074 的投影執行器。
3. **最可靠的輸入是工具自己的報告檔，而它現在沒有被保存**。設計文件說 file-watcher 會保留工具的輸出檔與 SHA-256；程式只記路徑、大小與修改時間（§1.2）。畫面輸出每個串流上限 100 KB，大範圍掃描會被截斷。要不要在指令結束時把報告檔收進證據，是擁有者的決定（§5 第 1 題）。
4. **技術標記現在的做法與設計原則不一致**。`commandTags` 在算雜湊之前把 `mitre_ttp` 寫進列裡，沒有記是哪條規則蓋的；[DESIGN-PRINCIPLES](../design/DESIGN-PRINCIPLES.md) §3 說 MITRE 標記是解讀，應該是標明為推測、可由操作者提升為標記的建議。建議改成：外掛的標記是可重算的建議，操作者確認的才是標記列（§3）。這會改變一個現有機制，是擁有者的決定（§5 第 3 題）。
5. **順帶的一件小事**：`_ingest.target_via`、`_ingest.door` 已經寫在每筆新列上，畫面沒有顯示。事件詳情加一行出處，不需要任何新資料（§4）。

## 1. 現況（從程式讀到的）

### 1.1 輸出存在哪裡

| 來源 | 存放 | 上限 |
|---|---|---|
| 外部終端機，relay 擷取（預設） | `command_end` 的 `stdout`／`stderr`，或 body store 的 `stdout_ref` | 每個串流 100 KB（`hooks/redlog-relay.py` `DEFAULT_MAX_BYTES`），超過記 `truncated` |
| 背景工作與串流輸出 | `command_output` 片段，以 `command_id` 連回指令 | 同上 |
| `pty` 類（`ssh`、`socat`、`pwncat-cs`） | 整段 PTY 輸出 | 同上 |
| `native` 類（`nc`、`ncat`、編輯器、分頁器） | 不擷取 | — |
| 內建終端機 | cast 檔，`command_end.io` 指向位移範圍 | 依 cast |

輸出的完整程度已有封閉的狀態（`src/core/content-contract.ts` 的 `ContentState`：`available`、`empty`、`not-captured`、`unreadable`、`truncated`）。結構化的結果必須帶著它：從截斷的輸出解析出來的清單不是完整的清單。

### 1.2 工具自己的報告檔：設計說有保存，程式沒有

[DESIGN-core-and-capture](../design/DESIGN-core-and-capture.md) §2.4 的決定是「保留工具自己的輸出檔（`nmap.xml` 之類）與它的 SHA-256」。`src/main/services/file-watcher.ts` 的 `emit` 只寫 `path`、`size`、`mtime`、`is_dir`；沒有讀檔、沒有雜湊、沒有複製。file-watcher 本身也是選用、預設關閉的。

只有操作者手動加入的檔案（`artifact_added`，`src/main/ipc/artifacts.ts`）會被存起來並算 SHA-256。

所以今天：`nmap -oX scan.xml …` 跑完，RedLog 知道指令、有（可能被截斷的）畫面輸出；`scan.xml` 的內容不在 RedLog 裡，之後被覆蓋或刪除就沒有了。這是設計文件與程式的落差，依 [AGENTS](../../AGENTS.md)「標準與程式不一致時回報」記在這裡。

### 1.3 已有的推導機制

| 機制 | 何時執行 | 結果在哪 | 可重算嗎 |
|---|---|---|---|
| 目標擷取（`targetExtractors`，`plugins/builtin-tools`） | 寫入前 | `target_id`，在鏈上 | 否 |
| loot 偵測、pivot／清理／檔案傳輸／憑證使用的伴隨列 | 寫入後，另寫一列 | 伴隨列，在鏈上 | 否 |
| 指令標籤（`commandTags` → `mitre_ttp` 等，`src/core/command-tagger.ts`） | 寫入前（`ingest.ts` 的 enrich） | 該列的資料欄位，在鏈上 | 否 |
| 全文索引（`cast-index.db`、`http-body-index.db`） | 寫入後或讀取時 | 另一個資料庫檔 | 是 |
| Spec 074 的投影（`derived.db`） | 草稿，71 項任務完成 5 項 | — | 是（設計如此） |

`cast-index.ts` 的檔頭把理由寫得很清楚：衍生的、會改寫的、可重建的東西不該放在以不可變為基礎的證據資料庫裡，也不該隨交付包出去。

### 1.4 其他

- `package.json` 沒有 XML 解析的相依套件。
- 工具知識分在兩處：`hooks/command-class.json` 的 `terminalProfiles`（擷取方式）與 `plugins/builtin-tools/plugin.json` 的 `targetExtractors`（三十多條）。
- 蓋章為規則紀錄預留了 `_ingest.rules`／`rules_partial`（`src/core/ingest/stamp.ts`），還沒有寫入者。

## 2. 工具輸出的事實

### 2.1 界線

記：工具自己回報的內容，照它回報的樣子——主機、位址、port、協定、狀態、狀態的理由、服務名稱、產品與版本字串。

不記：這是不是弱點、多嚴重、怎麼修、任何評分。也不替工具的輸出加上它沒說的結論（例如從版本字串推斷 CVE）。

解析出來的內容不是第一手擷取。依 [DESIGN-PRINCIPLES](../design/DESIGN-PRINCIPLES.md) §3，它要標明是解析來的、能指出是哪個解析器的哪一版。

### 2.2 三種輸入與它們的可靠度

| 輸入 | 格式穩定度 | 完整度 | 今天有嗎 |
|---|---|---|---|
| 工具的機器可讀報告檔（`-oX`、`-oA`、`-o json`） | 高（有 schema） | 完整；中斷的掃描檔案不完整但可辨識 | **沒有保存**（§1.2） |
| 畫面輸出（`stdout`） | 中（隨版本與選項變） | 100 KB 截斷；`-v` 之類的選項混入進度行 | 有 |
| 內建終端機的 cast | 低（含游標控制碼） | 完整 | 有 |

第一版只處理前兩種。報告檔優先；沒有報告檔時用畫面輸出，並把完整度帶進結果。

### 2.3 一筆事實的形狀

```
ToolFact {
  sourceEventId      // 產生它的列：指令的結束列，或報告檔的產物列
  observedAt         // 那一列的事件時間
  tool, parser       // 例如 'nmap'、'nmap-xml@1'
  input              // 'report-file' | 'stdout'
  complete           // 輸入完整且解析走到結尾
  kind               // 'host' | 'port'
  host               // 工具回報的名稱或位址，原樣
  address?, port?, protocol?
  state?, reason?    // 'open'／'closed'／'filtered'…，原樣，不翻譯
  service?, product?, version?
}
```

- 值原樣保存，不正規化成 RedLog 自己的詞。顯示時再對應。
- `host` 與 RedLog 的目標以既有的主機比較（Spec 038 的比較函式）對應，只用於把事實列在某個目標底下，**不寫回任何列的 `target_id`**。
- 同一個 port 被兩次掃描看到是兩筆事實，各自連回自己的指令。「現在開著哪些」是對事實的查詢（每個主機／port 取最新一筆），不是另一份狀態。這樣「兩次掃描之間變了什麼」自然可查。

### 2.4 解析器的約束

1. **純函式**：`(文字或位元組, 選項) → { facts, complete, problems }`，不碰資料庫、不碰檔案系統。
2. **輸入是對方可以影響的**。服務的 banner 由目標提供；報告檔在操作者的磁碟上，可被任何同使用者的程式改寫。所以：
   - 有大小上限、事實筆數上限、每個欄位的長度上限；超過就停下並標 `complete: false`。
   - XML 不解析 DTD 與外部實體；nmap 的 XML 只需要少數幾個元素與屬性，以受限的方式讀取即可，不需要通用的 XML 函式庫。
   - 控制字元在顯示前處理；解析出來的字串不進任何 shell、路徑或查詢字串。
   - 有時間預算，在主執行緒之外執行（今天可用 `bounded-regex.ts` 的 worker 做法，之後是 074 的 `heavy` 執行緒）。
3. **解析出來的內容不得用於歸屬或範圍判定**。入口已有這條規則（`causes-resolver.ts`：從輸出位元組讀出來的東西是對方控制的）。事實只用於顯示與搜尋。
4. **有版本**。解析器改了，版本就變；結果帶版本，重算時整批替換。
5. **失敗不影響原始列**。解析丟錯就是「這一筆沒有結構化的檢視」，附原因。

### 2.5 存在哪裡：三個做法

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. 寫成鏈上的推導列（像 loot） | 現成的機制；隨交付包出去 | 解析器的錯永久留在證據裡；改版後新舊列並存；每個 port 一列會把時間軸淹掉 |
| B. 投影（`derived.db` 的一張表，Spec 074 的 `Projection`） | 可重算；不碰證據；跨指令查詢便宜 | 要等 074 的投影執行器（目前 5／71） |
| C. 就地解析（開啟一筆指令的詳情時解析那一筆） | 不需要任何儲存；今天就能做 | 只能回答「這一筆指令看到了什麼」，不能跨指令查 |

建議：**先 C，後 B，不做 A**。解析器是同一份純函式，C 與 B 只差在誰呼叫它、結果放哪。

交付包不帶事實。收到交付包的人有原始輸出與報告檔，可以用同一個解析器重算；驗證器不需要認得它。

### 2.6 顯示與查詢

| 位置 | 內容 | 需要哪一期 |
|---|---|---|
| 指令的詳情 | 輸出之上一個「結構化檢視」：主機與 port 的表；標明輸入是報告檔或畫面輸出、是否完整、解析器版本；原始輸出一鍵可見 | C |
| 指令列 | 一行摘要：「3 台主機、12 個開放的 port」 | C（詳情開啟後）；清單上要等 B |
| 目標頁 | 該目標底下看到的服務，每一項連回看到它的指令與時間 | B |
| 搜尋 | `port:445 state:open service:smb` 這類條件 | B；語法歸統一查詢引擎 |

不做：獨立的「資產」頁、服務的編輯、手動新增事實、嚴重度欄位。

### 2.7 工具知識集中成一筆

結構化會讓「RedLog 認得這個工具」的知識變成三處。建議在做結構化的同時定下形狀：一個工具一筆宣告，列出它的執行檔、擷取方式、目標擷取策略、報告檔的旗標與格式、對應的解析器。

```
{ "id": "nmap", "executables": ["nmap"],
  "capture": "relayed",
  "target": { "strategy": "lastIpOrDomain" },
  "reports": [ { "flag": "-oX", "format": "nmap-xml" }, { "flag": "-oA", "format": "nmap-xml", "suffix": ".xml" } ],
  "facts": "nmap" }
```

解析器本身是核心裡的程式（「內建」的意思）；宣告是資料。第三方不能提供解析器的程式碼（Spec 076：第三方程式碼不進行程），之後若要開放，是宣告式的（欄位對應），那是另一個決定。

這一項牽涉 `command-class.json` 與 `builtin-tools` 兩份既有資料的合併，以及 Spec 076 的 manifest。可以先在核心內合併成一張表，manifest 的形狀等 076。

### 2.8 分期

| 期 | 內容 | 依賴 | 規模 |
|---|---|---|---|
| 0 | nmap 解析器（XML 與一般畫面輸出），純函式；樣本來自真實輸出（多個 nmap 版本、`-sV`、`-O`、`-Pn`、IPv6、多主機、中斷的掃描、被截斷的輸出）；惡意輸入的測試（超長 banner、控制字元、巢狀與未閉合的 XML、十萬個 port） | 無 | 小 |
| 1 | 指令詳情的結構化檢視（就地解析畫面輸出） | 期 0 | 小 |
| 2 | 指令結束時保存報告檔（§5 第 1 題）；結構化檢視優先讀它 | 擁有者的決定；寫入契約要能帶附件 | 中 |
| 3 | 投影、目標頁、搜尋條件 | Spec 074 的投影執行器 | 中 |
| 之後 | 第二個工具 | 依實際使用決定 | — |

期 0 與期 1 不改任何證據、不加任何儲存、不依賴未完成的規格。

### 2.9 驗證

- 解析器：每個樣本一份預期的事實清單（資料檔），加上性質測試：任何輸入都不丟錯、都在預算內結束、`complete` 為真時事實數等於輸入裡的 port 數。
- 就地解析：同一筆指令解析兩次結果相同；解析失敗時詳情照常顯示原始輸出。
- 投影（期 3）：增量推進與從頭重建的結果相同（074 既有的等價測試方式）。
- 真實視窗：以一次真的 nmap 掃描走過「執行 → 詳情看到表 → 點回原始輸出」。

## 3. ATT&CK 技術標記

### 3.1 現況

- 外掛可在 manifest 宣告 `commandTags`：樣式符合就在 shell 的 `command_start` 上蓋 `mitre_ttp`、`technique_tool`、`technique_category`（保留欄位），先符合的先得。核心刻意不內建任何樣式。
- 蓋章發生在寫入前，欄位進雜湊。
- 沒有記是哪個外掛的哪條規則蓋的。
- 畫面、搜尋、匯出都沒有讀這些欄位。
- 目前沒有任何內附或官方的外掛提供樣式。

三個問題：標記是解讀卻被寫成列的一部分（[DESIGN-PRINCIPLES](../design/DESIGN-PRINCIPLES.md) §3）；對照表更新後舊列無法重標；寫了沒有人看得到。

### 3.2 建議的模型：建議與確認分開

| | 外掛的建議 | 操作者的確認 |
|---|---|---|
| 是什麼 | 規則符合某個指令時的推測 | 操作者說「這是 T1046」 |
| 存在哪 | 可重算的推導（期 0 就地計算；之後是投影） | 一筆標記列，引用那個事件，帶技術編號 |
| 在鏈上嗎 | 不在 | 在（它是操作者的主張，與既有的標記相同） |
| 對照表更新後 | 重算 | 不變 |
| 顯示 | 標明是建議、來自哪個外掛與哪個 ATT&CK 版本 | 與其他標記相同 |

這正是 §3 的「建議可由操作者提升為權威標記」。它也讓手動標記不需要另一套機制：標記多一個選填的技術編號欄位。

連帶的改變：`commandTags` 不再把欄位寫進列裡。現有的列不動（列不改寫）；新列不再帶 `mitre_ttp`。因為目前沒有任何外掛提供樣式，實際上沒有資料受影響〔未以真實專案的資料庫確認〕。

### 3.3 外掛的形狀

一個 Processor 外掛，只有資料：

- 規則：指令樣式 → 技術編號（可多個）、信心（沿用既有的 `Confidence`）。
- 技術表：編號 → 名稱、戰術；註明 ATT&CK 的版本與領域（enterprise）。
- 外掛的版本與內容雜湊由 Spec 076 的 manifest 提供；建議的來源以此標示。

規則在有時間預算的 worker 裡執行（既有的 `bounded-regex`）。對照表本身的品質是外掛作者的事；核心只保證「這是建議、來自誰、哪一版」。

MITRE ATT&CK 的內容可依其使用條款引用，需標示來源〔條款細節未查〕。

### 3.4 顯示、搜尋、匯出

- 事件詳情：技術編號與名稱，分「建議」與「已確認」。
- 搜尋：`technique:T1046`，兩種都找，可只找已確認的。
- 對齊列（Spec 076 FR-084）：新欄位只能附加在尾端；加一欄 `technique`，只放已確認的。建議不進交付，除非擁有者另外決定。
- ATT&CK Navigator 的 layer：由對齊列轉出，是轉換程式或匯出外掛，核心不畫矩陣。

### 3.5 分期

| 期 | 內容 | 依賴 |
|---|---|---|
| 0 | 標記的技術編號欄位；詳情顯示；搜尋條件 | 無 |
| 1 | 建議改為可重算（`commandTags` 不再寫進列）；詳情顯示建議與來源 | §5 第 3 題 |
| 2 | 官方的規則外掛 | Spec 076 的 manifest；期 1 |
| 3 | 對齊列的欄位；Navigator 轉換 | Spec 076／077 |

期 0 本身就有用：操作者今天就能手動標，而且它不依賴任何外掛。

## 4. 出處：寫了但看不到

| 欄位 | 何時開始寫 | 畫面 |
|---|---|---|
| `_ingest.door` | Spec 071 Phase 3 | 只有交接徽章 |
| `_ingest.producer`、`auth` | 同上 | 沒有 |
| `_ingest.target_via` | #800 | 沒有 |
| `_ingest.terminal` | 同上 | 終端機帶間接用到 |
| `mitre_ttp` 等 | 更早 | 沒有 |

建議在事件詳情加一行白話的出處，由一個純函式從蓋章組出：

- 「由 shell hook 經 API 寫入。目標 10.0.0.5 取自指令文字。」
- 「由 RedLog 自己寫入。目標是操作時選定的目標。」
- 「背景輸出，目標沿用它所屬的指令。」
- 沒有蓋章的舊列：「這筆紀錄早於來源蓋章。」

清單不顯示出處，只在詳情。來源目前只能說到入口與類別（外部來源都是 `legacy`）；等 Spec 071 Phase 4 的憑證才說得出是哪個工具，文字屆時跟著變準確，不需要改結構。

這一項不需要擁有者決定，也不依賴其他規格。

## 5. 需要擁有者決定的事

每題一個情境。建議在前。

**第 1 題：指令結束時要不要把工具的報告檔收進證據？**

情境：操作者跑 `nmap -sV -oX scan.xml 10.0.0.0/24`。

- (A，建議) 收。指令結束時讀它在指令列上指名的輸出檔，存進 body store、算雜湊、連到那個指令。有大小上限，超過只記路徑、大小與雜湊。只認工具宣告裡列出的旗標。
- (B) 不收，只在操作者手動加入時才有。結構化只靠畫面輸出，大範圍掃描會不完整。
- (C) 不收內容，但記雜湊。之後能證明檔案沒被改過，但檔案不見就無法重算。

理由：這是設計文件原本的決定（§1.2），而且是唯一完整的輸入。代價：RedLog 會主動讀操作者磁碟上的檔案，這是今天沒有的行為；WSL 與遠端的檔案讀不到。

**第 2 題：第一版的結構化檢視放在哪裡？**

- (A，建議) 只在指令的詳情裡。不需要新的儲存。
- (B) 同時做目標頁的服務清單。要等 Spec 074 的投影，或先做一個之後要拆掉的臨時儲存。

**第 3 題：外掛的技術標記要不要改成不進雜湊鏈的建議？**

情境：外掛的規則把 `nmap -sS` 對到 T1046；半年後對照表更新，同一類指令改對到另一個子技術。

- (A，建議) 改。外掛的結果是可重算的建議；操作者確認的才寫成標記。現有的 `commandTags` 不再把欄位寫進列。
- (B) 維持寫進列，補上是哪條規則蓋的。舊列保留舊的對應，永遠如此。
- (C) 兩者都留：寫進列，另外也能重算。兩份答案可能不同。

**第 4 題：建議的技術編號要不要隨交付資料出去？**

- (A，建議) 不要，只有操作者確認的才出去。
- (B) 都出去，分兩欄。

**第 5 題：第一個工具之後做哪個？**

不建議現在決定。等期 1 用過一陣子，依實際最常被打開結構化檢視的工具決定。

## 6. 與其他規格的關係

| 規格 | 關係 |
|---|---|
| 071（蓋章、寫入契約） | 期 2 的報告檔要經寫入契約帶附件；`_ingest.rules` 若第 3 題選 (B) 才用得到 |
| 072（種類登記表） | 報告檔的產物列是一個種類；事實不是事件，不進登記表 |
| 074（投影） | 期 3 的儲存；它的「增量等於重建」測試直接適用 |
| 075（來源狀態） | 無直接關係 |
| 076（擴充功能） | 技術標記外掛的 manifest；工具宣告之後的歸屬 |
| 077（交付邊界） | 事實與建議都不進交付；確認過的技術編號經對齊列出去 |

沒有一項需要插進 Spec 071 Phase 3 剩下的工作之前。期 0、期 1 與 §4 可以在任何時候獨立進行。

## 7. 風險

- **把推測顯示得像事實。** 結構化檢視與技術建議都要在畫面上標明來源與完整度；這是整件事最容易做錯的地方。
- **解析器被惡意輸入拖垮或誤導。** §2.4 的上限與預算；惡意樣本進測試。
- **功能蔓延。** 一旦有了主機與服務的表，下一步很自然會想加弱點、加備註、加狀態。界線寫在 [PRODUCT-POSITIONING](../PRODUCT-POSITIONING.md)；每次想加欄位時回去對照。
- **做兩次。** 在 074 之前做跨指令的儲存，之後要拆。所以期 3 明確排在 074 之後。

## 8. 未量測與未驗證

- nmap 各版本一般畫面輸出的格式差異（需要蒐集真實樣本）。
- 100 KB 的上限在實際掃描中多常被碰到。
- 就地解析一筆大輸出的耗時。
- `commandTags` 是否有任何使用者外掛在用、既有專案的列裡有沒有 `mitre_ttp`。
- ATT&CK 內容的使用條款細節。
- 其他工具的機器可讀格式（`ffuf -o`、`nxc` 的資料庫、`masscan -oJ`）沒有逐一看。
