## 1. 目標與完成定義

新增同類擷取來源時，只新增來源 Adapter、宣告與測試，不修改活動列表、時間軸、Inspector 或對應 Reader。新增真正不同的內容能力時，仍允許擴充核心契約與共用 Reader，不能承諾所有未來來源零修改。

活動紀錄負責查找，時間軸負責時間與並行關係，Reader 負責忠實閱讀已保存內容。三者共用權威事件資料與內容服務，不各自解析來源原始格式。

關鍵驗收：用兩個既有 AI 來源建立契約，再接入第三個測試來源；第三個來源不得修改上述通用 UI。停用、移除或升級插件後，舊紀錄仍能搜尋、開啟並讀取已保存內容。

## 2. 現有基礎與限制

- `src/core/plugins/types.ts` 已有 `EventTypeContribution`（agentType、標籤、lane、顏色、圖示）、capture 與宣告式規則；不是從零建立插件系統。
- `src/core/plugins/manifest.ts` 明確拒絕未實作的 mappers、exporters、monitors。不能只新增宣告名稱，就聲稱已有執行能力。
- 現有 producer 將正規化事件送至既有事件接收入口；本計畫不恢復未實作的通用 raw ingest host。
- 優先沿用 `content-contract.ts`、`evidence-content.ts`、`saved-content-delivery.ts` 與 `EventContentReader.tsx` 的內容參照、分段讀取、搜尋定位、複製／保存能力。
- 現有 privileged tailer 未隔離，只允許隨附插件並受既有信任流程控制。本計畫不放寬第三方程式執行權限。
- 原型中的假 Session 切換、虛構 Header、假圖片與假匯出，是設計／原型缺陷；不能據此宣稱正式產品有相同缺陷。

## 3. 責任分工

| 層級 | 擁有的責任 | 不應承擔 |
| --- | --- | --- |
| 來源 Adapter | 來源格式解析、事件與內容描述、來源識別及順序 | 任意修改證據、提供 CSS／HTML、直接控制主 UI |
| 核心接收與內容服務 | 專案歸屬、驗證、事件識別、保存、索引、參照解析、交付政策 | 猜測未觀測到的資料或結果 |
| 核心 registry 與投影 | 宣告解析、相容性、共用能力選擇、狀態文字與圖示 | 動態執行第三方 renderer |
| 共用 UI | 列表、時間軸、詳情、導航與 Reader | 每個頁面各自撰寫來源判斷與解析器 |

內建來源先使用相同 registry 介面，但不強制改成可卸載插件；避免讓核心功能依賴插件安裝狀態。

## 4. 契約設計要求

下列是待映射到現有型別的語意要求，不是可直接使用的新 plugin.json schema。禁止先建立第二套資料庫事件模型再要求所有來源遷移。

### 來源、事件種類與 Reader 的對應

| 概念 | 回答的問題 | 使用位置 |
| --- | --- | --- |
| Source | 哪個 producer 產生這筆資料？ | 專案來源篩選、來源診斷、Session 識別 |
| Event Kind 與版本 | 這筆資料描述什麼事實？各欄位有何語意？ | 驗證、索引、列表摘要與時間軸分組 |
| Reader 能力 | 哪種核心閱讀器能呈現已保存的內容？ | Inspector 的展開閱讀、命中位置與返回 |

多個來源可產生同一 Kind，同一來源也可產生多個 Kind。兩種代理工具的工具回傳都可映射至 `ai.conversation` 內的 Tool Result 訊息，由共用 Transcript 根據專案、來源、Session 及 Tool Call ID 定位。兩種 HTTP producer 的 `http.exchange` 共用 HTTP Reader，只呈現各自實際取得的欄位。Scope 判定應保留被觀測事件、比對規則及依據，由核心產生可追溯結果。

正式 repo 已在 `src/core/plugins/contributions.ts` 透過 `registerEventTypes` 註冊 `eventTypes`。現有 `EventTypeContribution` 以 `agentType` 提供標籤、泳道與圖示等資訊。批次 A 要先決定既有 agentType／subtype 如何對應 Kind，再擴充現有入口或接上核心能力表。Kind 名稱、修訂語意與 Phase 0–4 依[Activity Event Extension Contract v1（Proposed）](ACTIVITY-EVENT-EXTENSION-CONTRACT-v1.md)，實作前須以既有事件驗證映射。

來源篩選的選項取自專案可查詢的歷史來源，另標示目前安裝狀態。Reader、預設軌道及可索引欄位從核心依 Kind 與版本解析；索引只處理允許搜尋且實際保存的內容。未識別 Kind 時使用一般觀測軌道、通用 Reader 與核心既有交付政策。

### 4.1 身分、版本與時間

- 核心事件 ID 與來源事件 ID 分離。來源識別限定於專案、producer instance 與來源命名空間；Session／Turn／Message ID 不得只用畫面序號。
- 記錄 schema 版本及 Adapter 版本，與 plugin API 版本分開管理。
- 分開來源發生時間與核心收到時間；保存原始時間資訊與精度，未知時不能填成收到時間卻冒充發生時間。
- 時間表示區分瞬間、已知區間、已知開始但尚未結束、未知。零、缺失與進行中不是同一狀態。
- 同時間戳以來源順序與穩定事件 ID 等明確規則排序；跨來源只有時間資訊時，不宣稱存在全域因果順序。
- 重送去重、離線補送、晚到片段與更新需有明確規則。原始紀錄遵守既有證據保存機制；可重建投影不等於可覆寫證據。

### 4.2 狀態與事實

- 執行階段：running、waiting、ended、unknown／not-applicable。
- 執行結果：exit code、HTTP status 等來源事實；尚未產生結果不能標成功。
- 擷取完整性：完整、接收中、無內容、未提供、截斷、讀取失敗等，須映射現有內容契約而非建立互斥衝突的新列舉。
- 範圍判定由核心依規則與觀測事實計算；來源主張另存並標示依據，不得直接變成權威判定。
- 已保存、hash 相符、TLS 驗證等僅由相應核心操作／觀測結果提供。插件不可自填 verified 讓 UI 當成已驗證。
- 原始事件不存 badgeClass、任意 CSS、HTML 或翻譯後狀態文字。既有 event-type 色彩能力保留相容；新的描述優先使用核心語意 token。

### 4.3 內容與 Reader 能力

| 共用能力 | 必須保留的資訊 |
| --- | --- |
| command | command、cwd、exit code；stdout／stderr 參照與各自完整性；文字輸出與可回放資料分開 |
| http-exchange | 實際 Request／Response；可重複 Header；Body 類型、編碼、長度與完整性；允許缺 Response |
| conversation | Session／Turn／Message 穩定 ID、有序訊息、Tool Call ID／Result 對應、多段 Assistant；摘要不冒充完整結果 |
| attachment | 核心管理的附件參照、MIME、大小、可用性；圖片尺寸與驗證結果依實際資料 |
| observation | 觀測事實、欄位、來源與規則依據；一般內容及原始資料 fallback |

大型內容使用核心的 ContentRef／分頁能力，不能強迫塞進事件 JSON。列表摘要是衍生資訊，必須能定位到對應已保存內容。未知欄位與未知版本需可保留並以通用 Reader 檢視，不能直接丟棄整筆已保存事件。

### 4.4 搜尋與關聯

- 宣告可索引欄位與內容種類，由核心建立索引；不接受插件提供 SQL 或任意搜尋程式碼。
- 命中結果包含欄位、片段及版本化內容錨點。大內容的索引／讀取須有界，不能在 renderer 每次輸入掃描所有 payload。
- 明示搜尋是涵蓋全部已索引內容、部分內容或仍在索引；未索引不等於無結果。
- 關聯保存方向、類型、來源依據與來源識別。核心驗證目標專案與存在性；晚到目標可暫待解析。
- AI invoked Shell 是單一方向的關係，Shell 詳情反向呈現「由 AI 呼叫」，不另外捏造反向 invoked。
- 時間鄰近只提供附近事件導航，不轉成因果證據。

## 5. 宣告與信任邊界

- 先做受驗證的宣告式能力描述：命名空間、schema 版本、Reader 類型、欄位映射、內容參照及搜尋欄位。具體 Manifest key 在契約盤點後決定。
- 欄位映射限定可驗證的資料路徑與白名單轉換，不使用 eval、任意 JS、SQL 或任意 HTML。
- 複雜解析先放在現有受信任 Adapter 或既有外部 producer；新的第三方 executable host 不在本期範圍。
- 檔案參照只由核心解析；插件不透過任意路徑或 URL 讓 Reader 讀取檔案／發出請求。UI 不直接取得本機檔案權限。
- 顯示、複製與一般匯出共用敏感內容政策。原始證據保存政策與閱讀遮蔽分開，不為了顯示而改寫證據；原始交付走既有明確操作及權限機制。
- 宣告大小、內容量、映射深度及索引工作設限；插件失敗隔離到該來源，核心記錄與其他來源仍可運作。
- 插件停用後不再接入新資料，但歷史閱讀不能依賴它的程式碼。保存必要的版本化宣告／來源中繼資料，仍以核心驗證與 fallback 呈現。

退出條件：各來源現有能力無倒退，從列表或時間軸均能開啟相同內容與關聯。

退出條件：第三方宣告不需要注入 React／JS；核心可拒絕無效宣告並保留已保存資料。

## 7. 驗收矩陣

| 情境 | 可觀察結果 |
| --- | --- |
| 新來源停用後重啟並重建索引 | 歷史來源仍可從篩選器選取；用測試字串查到原事件，開啟已保存內容，按一般交付政策匯出後核對內容及遮蔽結果 |
| 第三個 AI 來源 | 只新增 Adapter／宣告／測試；列表、時間軸、Transcript 不改 |
| 兩來源相同 Session／Turn ID | 專案與來源命名空間隔離，內容與焦點不串用 |
| running → waiting → ended | 標題與身分不變，結果未產生時不顯示成功 |
| 亂序、重送、離線補送 | 不重複製造事件，不遺失片段，保留來源順序依據 |
| Tool Result 很大或只有摘要 | 分段讀取完整已保存內容；摘要／未提供狀態不冒充完整 |
| 搜尋 HTTP Body／Tool Result | 顯示命中片段，開啟後定位正確來源、版本及位置 |
| 遮蔽後複製／匯出 | 一般交付遵循同一政策，原始交付另有明確操作 |
| 篩選排除選取事件／零結果 | 列表、時間軸、詳情選取一致，沒有殘留錯誤事件 |
| 插件移除、版本不相容、描述損毀 | 停止新接入並診斷；歷史已保存內容有核心 fallback |
| 插件嘗試跨專案或非法內容參照 | 核心拒絕，不影響其他來源 |
| 舊專案開啟與索引重建 | 舊事件可讀；重建衍生索引不改寫證據鏈 |
| 桌面／最小視窗／鍵盤 | 列表→詳情→Reader→返回保留位置，載入／空／失敗皆可恢復 |

使用專案既有 gates 與相關單元／整合測試，再用隔離專案操作 Electron 完整路徑。效能先建立現有基準，再針對大量事件、內容分頁與索引量測，不先捏造延遲目標或以 mock 代替真實流程驗收。行動網頁只有實際列入交付才追加手機驗證。

## 8. 遷移與回退

- 先將既有來源包成 Adapter，保持現有 payload、API 與保存規則可讀。必要變更以顯式版本轉換處理。
- 衍生投影／索引可版本化重建，原始證據不可為遷移而重寫。
- 每批保留既有閱讀路徑作為受控回退；不得長期維護兩套互相矛盾的查詢或狀態。
- 新來源投影失敗時顯示診斷與通用內容，不讓整個列表／時間軸失效。
- 本期不包含公開 Marketplace、任意 UI 插件、任意 SQL／JS mapper、新 executable sandbox 或全面重做設定頁。

## 9. 與 Stitch 的分工

Stitch 只設計能力對應的共用布局、狀態與導航，不決定儲存 schema、插件 API 或信任策略。展示來源名稱可變，但不得替每個來源新增頁面或寫死資料欄位；也不得以假成功、假圖像、假 Session 切換代表契約已完成。

本計畫不取代目前 UI/UX 修正與證據閱讀缺陷的處理，也不以建立文件代表功能已完成。
