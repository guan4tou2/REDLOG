# Audit — 2026-08-08 (v0.9.3)

Findings from a four-agent read of the whole tree (positioning, backend,
renderer, extensibility). Each item is tagged:

- **[verified]** — reproduced by reading the exact lines cited.
- **[reported]** — surfaced by an analysis pass, not independently re-read.

Severity is operator impact, not code ugliness. Fix ordering lives in
`ROADMAP.md`.

**Status.** P0-1 through P0-3 (and the minimap half of P0-3) are fixed in
v0.9.4. P0-7 (2026-08-09) generalises P0-4 and is fixed in v0.9.6. P0-4 and P0-5 were found on 2026-08-09 — the first while verifying those
fixes against the built app, the second from an operator report — and are
also fixed in v0.9.4. Everything else below is open.

## 1. Correctness — data loss / silent failure

### P0-1 `os.homedir()` with no `os` binding **[verified]** — ✅ fixed in v0.9.4

`src/main/index.ts:549` calls `os.homedir()`, but line 4 imports only
`{ homedir } from 'os'`. There is no `os` identifier in scope, so the call
throws `ReferenceError` on every `startProject()`. Line 555 swallows it:

```ts
} catch { /* missing / bad file → default no-filter */ }
```

**Impact.** `excludedPaths` and `watchPaths` are permanently `[]` for the
agent tailer. Every path an operator excludes in Settings ▸ Integrations is
ignored on that ingest path. The shell hook reads the same file itself, so
its gate still works — which is exactly why this has gone unnoticed: the
feature appears to work when tested with a shell command.

This also means README's "two-gate hook privacy" claim is only half true
today. Fix: `homedir()`.

### P0-2 Timeline lanes are silently clipped **[verified]** — ✅ fixed in v0.9.4

`Timeline.tsx:2323` sets `overflow-y-hidden`, while `laneH` has a floor of
`MIN_LANE_H = 36` (`:975-980`). 18 lanes × 36 px = 648 px + 28 px axis. On a
1080p window, after the header (~40), minimap (36) and the event list
(22 vh), the track container is often ~400 px — so roughly the bottom third
of the lane stack is cut off with no scrollbar and no indicator.

**Impact.** `scope`, `process` and `system` are last in `LANES` order, so
scope violations — a headline feature — can be invisible. Fix:
`overflow-y-auto` on the track container, plus a compact mode when the lane
count exceeds what fits.

### P0-3 Markers can be drawn outside the track **[reported]** — ✅ fixed in v0.9.4

The time domain is derived from `events[0].timestamp` /
`events[last].timestamp` (`Timeline.tsx:1087-1092`), but dots are positioned
with `displayTs()` (`:1249`), which honours a marker's `data.atTimestamp`
override. A marker dropped outside the current event range gets a negative
`toX()` or one past `TRACK_W` and disappears.

Related: the minimap density histogram bins on `e.timestamp` (`:1339`) while
the track uses `displayTs`, so the two disagree for overridden markers.

Fix: compute the domain from `displayTs` min/max.

### P0-4 Retention never runs in a packaged build **[verified]** — ✅ fixed in v0.9.4

Found while driving the built app to verify the other P0s (2026-08-09).

`src/main/index.ts:457` loads the retention sweep through a runtime
`require('../core/retention')`. Rollup cannot see through it, so the module is
never bundled — `out/main/` contains `index.js` plus four chunks, none of them
retention — and the string `require("../core/retention")` survives verbatim
into the output, where it resolves against a non-existent `out/core/`. Every
`startProject()` throws `MODULE_NOT_FOUND` into the catch on line 462:

```
[retention] sweep failed: Error: Cannot find module '../core/retention'
```

**Impact.** `terminal.castKeepDays` and `screenshots.keepDays` have no effect
in any shipped build: `.cast` files (up to 50 MB each) and screenshots grow
without bound, and the `system.cast_pruned` / `system.screenshot_pruned`
audit events that are supposed to explain a deleted file are never written.
Unit tests pass because `test/` imports `core/retention` directly and never
goes through the bundle.

The justifying comment is also wrong: it says "same pattern as
recoverOrphanSessions above", but `recoverOrphanSessions` is a **static**
import (`index.ts:38`). There is no such pattern.

Fix: static-import `sweepRetention` like every other core module.

### P0-5 HUD overlay drifts left and clips its content **[verified]** — ✅ fixed in v0.9.4

Reported by the operator on 2026-08-09 as "the HUD is broken — content is
mangled and it's in the wrong place". Three defects in the `overlay:autosize`
contract, all reproduced in `e2e/hud-overlay.spec.ts`:

**a. One-directional x correction.** `src/main/index.ts` only ever slid the
HUD *left* to keep a widening window on screen, and never restored it when the
window narrowed again. Measured: starting at `x=1309`, growing to 720px moved
it to `x=1080`, and shrinking back to 440px left it at `x=1080` — a permanent
229px drift. Every HUD-scale change or `emphasizeExternalIp` toggle walked it
further left until it pinned against the screen edge. Fixed by anchoring to
whichever display edge the HUD currently sits nearer, so width changes are
symmetric.

**b. Width was guessed, not measured.** `OverlayApp.tsx` reported
`440 * scale (+44 if emphasizeIp)` — a formula that (i) read the **raw** config
`scale` while the render clamps it to `[0.75, 2]`, so an out-of-band value
sized the window for one scale and drew at another, and (ii) cannot know the
real content width: a long external IP, a Wi-Fi name or an active pivot route
all overflow 440px. The panel's `overflow: hidden` then clipped it with no
indication. Fixed by measuring `scrollWidth` and keeping the formula as a
floor. The compact bar's own redundant `overflow: hidden` was removed so the
measurement is possible — the panel above it already clips.

**c. Hard 720px ceiling.** The Settings UI offers HUD scale up to 1.5, which
with emphasised IP needs ~726px of content — past the cap, guaranteed
clipping. The ceiling now scales with the display (`max(720, 60% of the work
area)`). The height ceiling had the same class of bug: it came from the
**primary** display regardless of which screen the HUD was on. Both now
resolve the HUD's actual display once and share it.

### P0-7 Runtime `require()` never survives bundling — four more instances **[verified]** — ✅ fixed in v0.9.6

v0.9.4 P0-4 treated `require('../core/retention')` as a one-off. It was a
family. Going looking turned up four more, all in the same shape, all
surviving verbatim into `out/main/` where they resolve against directories
rollup never emitted, all swallowed by a surrounding `catch`:

| Site | What silently stopped working |
|---|---|
| `chain-anchor.ts:203-204` (`./db/events`, `./db/operators`) | **`system.anchor_failed` was never written.** `audit-trail.md` lists it as a drift signal, and the v0.6.88 commit added it precisely because "an anchor failure is currently silent — the operator has no idea why it stopped renewing". In every packaged build it stayed silent. |
| `terminal-manager.ts:122-123` (`../core/db/index`, `../core/db/events`) | **`recoverOrphanSessions()` always returned 0.** A terminal killed by a crash never got its synthetic `session_end`, so its cast SHA-256 was never recorded and the timeline showed a session that never closed. |
| `cloud-share.ts:271` (`./db/index`) | `projectDirSafe()` always fell to its `~/.redlog/no-project` fallback, so cloud-share previews counted screenshots and casts in the wrong directory. |

Unit tests could not catch any of it: they import the modules directly and
never touch the bundle. `test/cloud-share.test.ts` had gone further and
*encoded* the bug — a comment explained that `require()` bypasses `vi.mock`,
so its fixtures were written into the fallback path.

Fixed by static imports. `test/bundle-requires.test.ts` now scans `out/main/`
and fails on any relative `require()` that does not resolve to an emitted
file, which closes the family rather than the instances.

### P2-4 HUD geometry: two real defects, both reverted unfixed **[verified]**

v0.9.4 shipped fixes for these; the operator reported the result as worse than
v0.9.3 and confirmed v0.9.3 was correct, so the change was reverted verbatim.
Both defects are still present and are recorded here rather than re-patched
without a way to verify against the operator's actual setup:

**a. x drifts left and never returns.** `overlay:autosize` slides the HUD left
when a width increase would push it off screen, but nothing moves it back when
the width shrinks. Measured on the reverted (= v0.9.3) build: from `x=1309`,
growing to 720px moves it to `x=1080`; shrinking back to 440px leaves it at
`x=1080`. This fires on every `overlay.scale` or `emphasizeExternalIp` change,
so the HUD walks left over a session. Characterised in
`e2e/hud-overlay.spec.ts`.

**b. Width ceiling clips at HUD scale 1.5.** The handler clamps width to a hard
720px, but the Settings UI offers scale up to 1.5, which with
`emphasizeExternalIp` needs ~726px of content — the excess is clipped by the
panel's `overflow: hidden`. Test skipped, not deleted.

**c. Initial x ignores the work-area origin.** `windows.ts` positions the HUD
at `workAreaSize.width - 440`, measured from x=0. On a display whose work area
does not start at 0 — a left-side Dock, a vertical taskbar, a secondary
monitor — the HUD opens that many pixels short of the right edge. Measured with
a left Dock: work area `x=51 w=1749`, HUD at 1309 instead of 1360. Present
since the initial commit (`ec32bc6`), so it is the position operators are used
to; changing it is a UX decision, not just a fix.

Any future attempt needs verification against a real operator install rather
than a clean temp-HOME E2E run, which is where the v0.9.4 attempt went wrong:
every automated check passed while the shipped behaviour was worse.

### P1-1 `verifyChainFullAsync` can break concurrent writes **[reported]**

`chain-anchor.ts:755-777` awaits `setImmediate` while a better-sqlite3
iterator is still open. With `db.iterators > 0`, `Statement.run()` throws
`This database connection is busy executing a query` (`get()`/`all()` are
exempt, which is why the sibling pubkey lookups are fine).

**Impact.** For the duration of a full verify — tens of seconds on a 100k
chain — every `insertEvent()` fails: REST returns 500, capture-health goes
`dark`, hook events fall into the spool. The existing comment argues this is
safe "as long as no statements interleave"; background capture is precisely
an interleaving statement.

Fix: run the walk on a second read-only connection, or move it to a worker.

## 2. Security / trust-model gaps

### P1-2 Pause does not stop persistence, and two sources ignore it **[verified]** — ✅ fixed in v0.9.5 (option A)

`api-server.ts:459-465` calls `insertEvent()` first and `eventBus.publish()`
second; only `publish` respects `paused` (`event-bus.ts:20-24`). Pausing
therefore stops the UI feed and the webhook, but the row still enters the DB
and the hash chain.

Separately, `hooks/shell-preexec-hook.sh` and `hooks/mitmproxy-addon.py`
never check recording state at all (the Codex hook, the OpenCode hook and the
tailer all do). So the README promise that daily/hobby work stays off the
chain by default does not hold for commands typed in a hooked shell.

**Resolved in v0.9.5: option A.** The gate moved into `insertEvent()` (the
single write point, so all 46 call sites are covered) and `POST /api/events`
bails before any detector runs, answering `200 {skipped}` so `curl -sf` in the
hook does not spool and replay it. `system` and `marker` stay exempt. Both
original options are kept below for the record:

- **A — pause means "do not record".** Move the check before `insertEvent`,
  add the gate to the shell hook and the mitmproxy addon.
- **B — pause means "do not display".** Rename it in the UI, and drop the
  privacy claim from the README.

Silent option C (current behaviour) is the one that must not stand, because
it is a claim the log itself contradicts.

### P1-3 `tailers` bypasses the trust gate **[verified]**

`plugins/index.ts:27-33`:

```ts
if (p.status === 'error' || p.status === 'disabled') continue
applyContributions(p)                                    // "declarative parts are always safe"
if (p.tier === 'privileged' && p.status === 'active') host?.start(p)
```

`applyContributions()` handles `c.tailers` with a bare
`require(join(p.dir, c.tailers))` in the **main process** —
no `utilityProcess`, no capabilities, and no `status === 'active'` check —
even though `manifest.ts:11` lists `tailers` in `PRIVILEGED_KEYS`. A
`needs-consent` plugin's tailer module executes before the operator consents.

Currently latent: `contributions.ts:59` rejects `p.source !== 'bundled'`, and
no `plugins/` directory is shipped or packaged. But the structure is wrong
and will bite the moment a bundled plugin ships.

Fix: either isolate tailers like `mcpTools`, or make the first-party-only
restriction explicit — move `tailers` out of `PRIVILEGED_KEYS`, load it from
a hard-coded first-party list rather than a manifest field, and say so in
`plugin-development.md`.

### P1-4 Registry index is not signature-verified **[reported]**

`marketplace.ts:115-145` structurally validates `index.json` but never checks
a signature over it, while `PLUGIN_MARKETPLACE.md:120` states the opposite
("changes to `index.json` without a valid signature are rejected; TLS is not
enough"). Combined with the **Trust all suggested** button
(`Settings.tsx:2396-2407`), which pins every publisher key the registry
advertises, whoever controls the registry can bootstrap themselves into
signing privileged plugins.

The default registry host `https://plugins.redlog.dev/index.json`
(`marketplace.ts:20`) does not resolve today — if someone else registers it,
it becomes a supply-chain entry point.

Fix (any of): implement index signing; drop the claim from the doc; require
per-publisher confirmation instead of trust-all; remove the default URL until
the domain is held.

### P1-5 Revocations are never fetched **[reported]**

`loadRevocations()` (`marketplace.ts:149-158`) reads only the local
`~/.redlog/plugins/revocations.json`. Nothing fetches or verifies it. The
documented "poll a signed revocations.json, disable on hit" flow does not
exist, and the Revocations tab is permanently empty unless a file is placed
by hand.

### P1-6 `vps-deploy.sh` ships the primary token **[reported]**

`hooks/vps-deploy.sh:56,66` defaults to the **primary** operator token — the
one that can create operators, rotate other tokens, export the full bundle
and read all loot — and pushes it to a red-team VPS, the most exposed asset
in the engagement. It also silently breaks, because the primary token is
rewritten on every app start (`api-server.ts:919`).

Fix: require a secondary token; refuse to run with the primary and print the
`redlog-cli operators add` command instead.

### P2-1 Content hash excludes capture hook scripts **[reported]**

`codeFilesOf()` (`manifest.ts:21-26`) returns only `PRIVILEGED_KEYS`, so a
🟢 plugin's `capture[].hookFile` — a shell script the operator sources into
`~/.zshrc` and runs on every command — is outside the pinned hash. Its
contents can change without triggering re-consent. Path safety is checked
(`collectFileRefs`), integrity is not.

### P2-2 Loot previews are plaintext in an unencrypted DB **[reported]**

`loot-detector.ts:183,211-215` stores up to 200 characters of the matching
line. There is no SQLCipher / `safeStorage` / at-rest encryption anywhere in
the tree. `operators.md:128-138` discloses local-root exposure honestly, but
for a tool whose stated job is handling credentials this belongs on the
roadmap rather than only in the threat model.

### P2-3 Cloud share worker never verifies uploaded bytes **[reported]**

`redlog-share-worker/src/index.ts:111-133` writes `req.body` into R2 without
recomputing sha256; the client does not send a checksum header either. Yet
`CLOUD_SHARE_BUNDLE.md:168` claims the worker rejects mismatched sanitize
counts — the worker does not parse `bundle.json` at all.

### P3 Smaller items **[reported]**

- `deconfliction.ts` imports both `http` and `https`; plaintext webhooks are
  possible with only a prose warning against them.
- `stopApiServer()` deliberately leaves `api-token` / `api-port` on disk, and
  `selfHealSidecarFiles()` rewrites them per request — the token outlives the
  app process.
- The WSL path sends the bearer token to a non-loopback gateway IP
  (`shell-preexec-hook.sh:55-63`).
- `data:revealPath` accepts an arbitrary path for `shell.openPath`.
- `redlog_recording` lets any token holder pause capture — including the
  agent being recorded.
