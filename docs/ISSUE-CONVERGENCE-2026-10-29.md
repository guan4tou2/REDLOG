## 一、Issue 盤點與處理原則

截至本次查詢，**共有 18 個 Open Issues，其中 4 個標示「暫緩」**。

這 18 個 Issue 不應全部當作待開發功能。其中有些已完成主要實作，只缺實機驗收；有些是跨功能規格或驗收矩陣；也有些應維持暫緩，不值得在目前版本繼續投入。

本規格採取以下原則：

1. **已實作不重做：** 先核對 v0.18.4 程式碼，再決定補測、修復或新增功能。
2. **修復與驗收分開：** CI 通過、原生實機通過、正式安裝包驗收通過，應保留不同狀態。
3. **可靠性優先於新功能：** 先處理漏記、錯誤歸屬、資料遺失、錯誤宣稱完整等問題。
4. **沿用既有架構：** 不重建 Shell recorder、HTTP proxy、ExportPlan、Reader 或整套 UI。
5. **明確收斂 Issue：** 每張 Issue 都必須能判定為完成、尚缺驗收、暫緩，或由其他規格追蹤。

### 優先級定義

| 等級 | 定義 |
|---|---|
| **P0** | 證據可能遺失、錯誤歸屬，或已承諾的保存完整性存在重大風險 |
| **P1** | 核心擷取、安裝、驗證、恢復、匯出流程無法可靠完成 |
| **P2** | 重要使用體驗、跨平台一致性、可觀測性或證據操作改善 |
| **P3** | 延伸能力、進階功能或非必要的 UX 改良 |
| **Deferred** | 暫緩實作，保留追蹤或等待實測證據 |

這是**建議的執行優先級**，不代表已修改 GitHub 的 Issue Labels。

以下是依照目前 18 個 Open Issues、Spec 062／064 及既有驗收契約整理的實作規格。**這是建議規格，尚未修改儲存庫或 Issue 狀態。**

## 三、共通產品契約

以下條件適用於所有後續 PR。

### SPEC-COMMON-01：來源狀態

沿用 `docs/domain/SPEC-capture-source-lifecycle.md`。

來源狀態：

`Unavailable → Available → Configured → Running → Verified`

另有 `Failed`、`Removed`。

這些狀態不可直接混用。

| 狀態 | 意義 | 不代表 |
|---|---|---|
| Configured | 已完成設定或接入 | 程式正在執行 |
| Running | Producer 或相關程序執行中 | 已收到有效證據 |
| Verified | 已有實際證據到達保存系統 | 目前所有活動都完整擷取 |
| Failed | 有已觀察到的失敗 | 歷史證據已消失 |
| Removed | 整合已移除 | 歷史記錄應被刪除 |

`lastEventAt` 是活動時間，不是健康狀態。

使用者沒有輸入指令、沒有 HTTP 流量，不能因此自動將來源標成故障。

### SPEC-COMMON-02：資料完整性

每份可保存的證據都應能追溯：

| 欄位 | 要求 |
|---|---|
| `engagementId` | 來源產生時即確定，不由目前 UI 專案猜測 |
| `sourceInstanceId` | 區分不同來源實例 |
| `sessionId` | 區分來源 Session |
| `commandId`／`taskId` | 有可信來源才建立 |
| `sourceTimestamp` | 原始來源時間 |
| `receivedAt` | REDLOG 接收時間 |
| `sequence` | 有來源序號時保留 |
| `contentRef` | 指向實際保存內容 |
| `hash` | 驗證已保存的實際位元組 |
| `coverage` | 明示已保存、部分保存或未知 |
| `gapReason` | 已知資料缺口原因 |

優先沿用既有欄位及資料模型，不要求再建立一份平行 Schema。

### SPEC-COMMON-03：不可違反的不變條件

1. 不能把 A 專案的事件送入 B 專案。
2. 不能把沒有來源證明的輸出歸到某道指令。
3. 不能把 `Running` 說成完整擷取。
4. 不能把 Reader 預覽截短說成來源內容截斷。
5. 不能把已傳送資料直接視為已持久保存。
6. 不能因為重試、更新索引或來源恢復而改寫原始證據。
7. 不得在未授權的 AI、剪貼簿或目錄來源擷取原文。
8. 不能因為匯出預覽後資料增加，就偷偷擴大匯出集合。

## 四、擷取可靠性規格

### SPEC-REL-001：來源中斷、Spool 與證據缺口

**對應 Issue：#291**
**優先級：P0**
**既有系統：** Spec 052、Ingest、Spool、Capture Gap、來源生命週期。

#### 4.1 使用者需求

當 REDLOG、來源程序、API 或儲存裝置發生問題時，操作者必須知道：

- 哪個來源受到影響。
- 哪個時間區間可能存在缺口。
- 哪些資料已經保存。
- 哪些資料仍在等待重送。
- 哪些資料無法確認是否遺失。

不能只在恢復後顯示綠色狀態。

#### 4.2 功能需求

**REL-001：來源身分綁定**

所有重送的事件必須保留產生時的專案與來源身分。不得使用目前開啟的專案重新歸屬舊事件。

**REL-002：Spool 重送**

沿用現有 Spool。必須驗證：

- 正常送出不產生不必要的 Spool。
- API 無法接收時依既有策略暫存。
- 恢復後只重送允許歸屬的事件。
- 同一事件重送不形成重複操作。
- 不可歸屬事件保持隔離。
- 已達容量上限時不得宣稱完整保存。

**REL-003：接收與保存邊界**

區分：`Produced → Received → Persisted → Indexed`

實作不一定需要增加四個 UI 狀態，但程式契約必須清楚。索引尚未完成，不代表原始證據未保存。已收到 HTTP 回應，也不能在未確認持久化語意前宣稱落盤完成。

**REL-004：停止與暫停**

驗證：`redlog stop`、`redlog start`、App 暫停、來源停用、專案切換、App 正常退出、App 異常終止。

停止後的舊背景程序不得繼續保存未授權的新內容。恢復後也不能自動補錄停止期間的敏感原文。

**REL-005：可觀測的資料缺口**

建議沿用既有 Capture Gap 表示方式，確保可以呈現：

| 原因 | 使用者應看到 |
|---|---|
| API 不可達 | 來源無法交付，可能已有暫存 |
| Spool 已滿 | 保存容量達上限 |
| 寫入失敗 | 部分內容未確認保存 |
| 來源突然結束 | Session 非正常結束 |
| 輸出截斷 | 已保存範圍及限制 |
| 專案切換 | 原 Session 停止記錄 |
| 無法歸屬 | 事件未加入目前專案 |

未知的遺失筆數必須顯示 Unknown，不得填入 0。

#### 4.3 驗收案例

| ID | 情境 | 預期 |
|---|---|---|
| REL-T01 | API 連線失敗 | 指令繼續執行，記錄失敗可追蹤 |
| REL-T02 | API 恢復 | 已允許的 Spool 正確重送 |
| REL-T03 | 同一事件重送兩次 | 不產生重複操作 |
| REL-T04 | A → B 專案切換 | A 的舊資料不進 B |
| REL-T05 | 停止後背景仍輸出 | 不保存未授權的新內容 |
| REL-T06 | 磁碟配額不足 | 不顯示假成功 |
| REL-T07 | App 強制終止後重開 | 已保存內容仍可讀，缺口可辨識 |
| REL-T08 | 無身分 Spool | 不自動歸屬目前專案 |
| REL-T09 | Source 沒有事件但仍存活 | 不因閒置而誤判故障 |
| REL-T10 | 匯出部分保存的 Session | 成品如實標示完整性 |

#### 4.4 完成條件

- Unit／Integration 通過。
- 故障注入通過。
- 至少一個真實 Shell Producer 通過。
- 重啟後能讀取已保存資料。
- Capture Health 與實際證據狀態一致。

**建議：這是所有擷取相關 Issue 的共同 Gate。**

### SPEC-SHELL-001：Zsh／Bash／PowerShell 透明擷取

**對應 Issue：#288、#434**
**優先級：P1**

#### 4.5 目前狀態

現有系統已包含 Shell Hook、Relay、PTY、接入與修復流程。

#434 的共用 `RecordTerminalFlow` 已經透過 PR #443 落地（元件由 `857a31cd` 引入，`src/renderer/src/components/RecordTerminalFlow.tsx`）。

因此不應重新開發終端錄製器，也不應再建立第二套設定精靈。

#### 4.6 功能規格

**SH-001：一次接入**

使用者選擇 Shell 後：

1. 顯示偵測到的環境。
2. 顯示實際修改的 Profile。
3. 執行接入。
4. 提示是否需要開啟新終端。
5. 執行驗證指令。
6. 顯示已收到的實際證據。

接入成功與收到輸出必須分開驗證。

**SH-002：終端透明性**

REDLOG 不應改變原本指令的 Exit code、Signal、Job control、stdin、TTY 行為、Pipeline、Redirect、Alias／Function、Unicode、顯示尺寸。

無法維持透明性的模式應標示限制，而不是強迫所有指令進入同一種錄製方式。

**SH-003：Session 身分**

不同終端分頁、tmux Pane、WSL 發行版、PowerShell Session 必須保留正確來源身分。相同 PID、相同命令文字，不能因此合併成同一操作。

**SH-004：互動式程式**

對以下操作驗證記錄開啟與關閉後的差異：`ssh`、`nc`、`socat`、`vim`、`less`、`tmux`、`sudo`、`python` REPL。

不要求全部都能拆出結構化命令，但必須保留原始可觀測能力，並清楚區分 metadata-only、PTY 合流與結構化輸出。

#### 4.7 跨平台驗收

| 平台 | 必測項 |
|---|---|
| Kali Zsh | 一般命令、失敗、輸出、PTY、tmux |
| macOS Zsh | Warp／其他終端、一般輸出、App origin |
| Linux Bash | Profile 接入、輸出與工作控制 |
| Windows PowerShell 5.1 | Profile、指令配對、輸出、退出碼 |
| Windows PowerShell 7 | 獨立 Profile 與能力驗證 |
| Windows＋WSL | Native/Windows 目錄辨識、Session、Spool |
| Git Bash | `MSYS_NO_PATHCONV=1` 與正常環境直送 |

#### 4.8 效能規格

量測：未啟用 REDLOG 的基準延遲、啟用後的額外延遲、Cold start、Steady state、100 道普通指令、大輸出、長時間互動。

#295 曾提出額外延遲 p95 ≤100 ms、p99 ≤250 ms 的目標。

**建議保留為量測目標，先取得各平台實測基準，再決定是否作為硬性 Release Gate。** 不可為了達標而停用必要保存或降低資料完整性。

#### 4.9 完成條件

- 實際安裝包可接入外部 Shell。
- 100 道實際指令的結果逐一對照。
- 失敗指令仍有正確 Exit code。
- Ctrl-C、Ctrl-Z／fg 不因 Recorder 失效。
- 不會重複執行使用者命令。
- 未支援模式有清楚限制。

### SPEC-STREAM-001：長時間輸出與串流保存

**對應 Issue：#290**
**優先級：P1**

#### 4.10 問題

長時間執行的指令、SSE、WebSocket、PTY Session 不能等到整段結束後，才一次保存所有資料。否則來源異常終止時，可能只留下開始事件。

#### 4.11 功能需求

**STR-001：分段保存**

已支援的持續串流使用有界分段保存。每段保留可取得的 Source Session、Flow／Recording ID、Sequence、Direction／Stream、來源時間、接收時間、原始位元組數量、保存狀態。

**STR-002：完整性狀態**

至少區分 `Complete / Partial / Truncated / Metadata-only / Unknown`。這是內容完整性，不應取代 Source Lifecycle。

**STR-003：中斷恢復**

來源意外結束後：已保存的區段仍可讀、缺少結尾應明示、不宣稱整段完成、不因重送而出現重複區段。

**STR-004：匯出**

匯出必須保留分段來源關係。對跨目標或含未確認片段的錄影，必須明示範圍與限制，不可把整段附件當成已清理的 Scope 內容。

#### 4.12 驗收案例

| ID | 測試內容 | 預期 |
|---|---|---|
| STR-T01 | 長時間 PTY 輸出 | 結束前能讀到已保存片段 |
| STR-T02 | SSE 持續傳送 | 依實際支援模式分段保存 |
| STR-T03 | WebSocket 雙向訊息 | 方向及順序正確 |
| STR-T04 | Binary Frame | 不錯誤轉成文字 |
| STR-T05 | 中途 Kill Producer | 已落盤資料可讀 |
| STR-T06 | App 強制結束 | 保留最後已確認保存範圍 |
| STR-T07 | 大量資料 | 記憶體與容量有界 |
| STR-T08 | 匯出部分錄影 | 正確標示 Partial |

不要求重新開發 mitmproxy 的協定實作。先盤點目前各來源的 flush／保存時機，再只修復不足的路徑。

## 五、HTTP 與網路擷取規格

### SPEC-HTTP-001：一次接入、持續可用、明確驗證

**對應 Issue：#289**
**優先級：P1**

#### 5.1 使用者需求

一般使用者應該能在需要網頁測試時完成一次設定。之後開啟已授權的專案，不需要反覆手動執行 mitmdump 或重新設定相同 Client。

#### 5.2 功能需求

**HTTP-001：單一主要入口**

使用既有「瀏覽器與 HTTP 擷取」，整合依賴偵測、mitmproxy 準備、Managed Proxy、Client 路由、CA 驗證、Capture Status、停止與修復。不另外開一套 Proxy 設定系統。

**HTTP-002：狀態必須分離**

| 項目 | 意義 |
|---|---|
| Proxy Ready | 代理程序可提供服務 |
| Client Routed | 指定 Client 的流量確認經過代理 |
| HTTP Verified | 收到實際 HTTP 交換 |
| HTTPS Decrypted | 成功取得該次 HTTPS 明文證據 |
| CA Trusted | 指定 Client 對該 CA 的信任已驗證 |

這些不是同一個布林值。HTTPS 使用 `-k` 或忽略憑證錯誤時，不能宣稱 Client 已正確信任 CA。

**HTTP-003：Proxy 環境變數**

受管終端啟用 Proxy 時：

- 不覆寫使用者既有設定而不告知。
- 保留必要 bypass。
- 清楚說明修改範圍。
- 不嘗試遠端改寫既有 Shell Process 的環境變數。
- 停止 Proxy 後提供可恢復操作。

對於已存在的代理鏈，應明示是否支援串接，避免產生代理循環。

**HTTP-004：重新啟動**

只有使用者先前明確啟用且仍有有效專案授權時，才能依既有設定自動準備來源。失敗時：保留設定、顯示實際原因、可重新驗證、不默默宣稱 HTTPS 仍在擷取。

**HTTP-005：Scope 不等於 Capture Filter**

Web Scope、Exclude、私人流量顯示與交付政策，不應被誤當作代理端自動停止擷取的保證。

#### 5.3 驗收案例

| ID | 情境 | 預期 |
|---|---|---|
| HTTP-T01 | 缺少 mitmproxy | 原地提供可執行的處理方式 |
| HTTP-T02 | 指定 HTTP Client | 真正收到 Request／Response |
| HTTP-T03 | HTTPS CA 未信任 | 不顯示已解密成功 |
| HTTP-T04 | HTTPS 正確信任 | 成功記錄指定 Client |
| HTTP-T05 | Proxy Port 衝突 | 明確錯誤與恢復 |
| HTTP-T06 | Proxy 程序死亡 | 狀態不再顯示 Running |
| HTTP-T07 | App 重啟 | 已授權來源依契約恢復 |
| HTTP-T08 | 切換專案 | 不把前一專案流量歸到新專案 |
| HTTP-T09 | 未經代理的 Client | 不宣稱被擷取 |

## 六、附件、截圖及匯出規格

### SPEC-ART-001：檔案證據與來源關聯

**對應 Issue：#292**
**優先級：P2**

#### 6.1 分階段策略

這個 Issue 應拆成兩個不同層次。

**第一階段：手動加入證據的可靠性。** 這是核心流程，應優先完成。

**第二階段：自動辨識工具輸出檔。** 這是便利功能，不應阻擋第一階段。

#### 6.2 功能需求

**ART-001：手動加入檔案**

操作者可選取檔案加入目前專案。必須保存當下內容或明確標示目前僅有檔案參照。已保存內容應具有版本、大小、Hash 及保存時間。

**ART-002：來源歸因**

| 關聯類型 | 定義 |
|---|---|
| Confirmed | 有可信來源可證明關聯 |
| Operator-assigned | 操作者明確指定 |
| Candidate | 根據參數或時間產生候選 |
| Unknown | 無足夠依據 |

例如執行 `nmap -oA scan`，只能產生輸出檔案候選，不能單靠參數推定指定檔案已由該命令成功寫入。

**ART-003：檔案版本**

驗證 Append、Overwrite、Delete、Symlink、同名替換、不同程序同時寫入、大檔、零位元組檔案。

後續來源檔案變更，不得改寫先前已保存版本。

**ART-004：截圖**

截圖時應保留觸發當下的專案、時間、可取得的 Target／Session、可取得的視窗資訊、實際保存結果。

如果無法確認目前視窗所屬 Session，應標示 Unknown，而不是強制綁定目前選取的 Target。

#### 6.3 驗收條件

- 手動加入的檔案重啟後仍可讀。
- 原檔被修改不影響已保存版本。
- 候選關聯不會顯示成已確認關聯。
- 截圖失敗不產生有效證據紀錄。
- 搜尋能從來源操作找到已保存附件。
- 匯出可逐項排除附件。
- 不會默默掃描整個使用者磁碟。

自動解析工具輸出參數的功能可留到後續版本。

不建議直接建立一個包含所有 Issue 的大型 PR。應按風險與驗收責任拆分。

| PR 批次 | 範圍 | 涵蓋 Issues | 主要交付 |
|---|---|---|---|
| **R01** | 既有修復驗收與文件 | #326、#345 | 實機結果、Issue 狀態、Release Notes |
| **R02** | 擷取可靠性 | #291 | Gap／Spool／Binding／Stop 契約與故障回歸 |
| **R03** | 終端實測 | #288、#434 | 真實 Shell 矩陣與必要修復 |
| **R04** | 長串流 | #290 | 持續落盤、截斷、中斷恢復 |
| **R05** | HTTP 接入 | #289、#293 | Client 路由、CA、能力宣告 |
| **R06** | 附件與證據 | #292 | 手動附件、版本、歸因 |
| **R07** | 匯出驗收 | #436 | Selection／Plan／成品一致性 |
| **R08** | 設定與來源管理 | #298、#435 | 剩餘 UX／授權／錯誤狀態 |
| **R09** | HUD、更新與原生驗收 | #317、#226 | 已有功能的完整操作證據 |
| **R10** | 最終收斂 | #295、#296、#317 | 需求追溯、覆蓋矩陣、未完成清單 |

這是建議的邏輯拆分，不要求每個批次都必然產生程式碼 PR。純驗收與文件修正可以獨立交付，某個批次沒有重現缺陷時不應為了產生 PR 而修改產品。

### PR 共同完成定義

每個 PR 必須記錄：Before／After 行為、對應需求、已有實作與本次增量、新增或修改的測試、完整回歸結果、實際執行環境、仍未驗證的限制、是否影響安裝包、是否影響資料保存或匯出、是否需要更新 Release Notes。

## 十二、最終驗收 Gate

### Gate A：擷取可信

- 核心來源身分正確。
- WSL 與 Git Bash 已知修復完成驗證。
- 跨專案無錯誤歸屬。
- 中斷與恢復可追溯。
- Stop／Pause 不保存未授權的新內容。
- 已知截斷或遺失不冒充完整。
- 支援的 Shell 能完成真實指令與輸出讀回。

主要追蹤：#291、#288、#326、#345。

### Gate B：接入可信

- 安裝包首次啟動。
- Shell 接入。
- 指定 Client 的 HTTP／HTTPS 驗證。
- 缺依賴可恢復。
- 來源狀態真實。
- AI 授權不擴大範圍。

主要追蹤：#226、#289、#293、#434、#435。

### Gate C：證據交付可信

- 手動附件可保存。
- Reader 可以讀回已確認版本。
- 片段來源可追溯。
- 預覽與成品一致。
- 排除附件不進成品。
- Verifier 正確識別損壞或修改。
- 失敗不產生假完成狀態。

主要追蹤：#290、#292、#436。

### Gate D：操作流程可信

- 小視窗可操作。
- 讀取失敗不顯示空資料。
- HUD 穿透可恢復。
- 更新稍後與取消不破壞工作。
- 三平台功能限制明確。
- 符合 Spec 062／064 對應操作驗收。

主要追蹤：#298、#317。

### Gate E：文件與發行一致

- Issue 狀態正確。
- Spec Tasks 與驗收證據一致。
- `test-coverage-matrix.md` 對齊實際版本。
- Release Notes 不漏掉重要修復。
- README 不超過已驗證能力。
- 安裝資產版本、Hash 與文件一致。
- 未驗證的平台明確保留 NOT RUN。

主要追蹤：#226、#295、#296、#317。

## 十三、建議最終執行順序

**第一階段：可靠性驗收** — R01 → R02 → R03。確認既有 WSL、Git Bash 修復有效，完成擷取、Spool、Shell 基礎可靠性。

**第二階段：保存完整性** — R04，並完成相關 R06 基本手動附件驗收。確認長時間操作不會因來源結束才保存而造成無法辨識的資料缺口。

**第三階段：HTTP 與來源整合** — R05，接著驗收 R08。先讓來源能力可靠，再統一呈現和操作。

**第四階段：交付** — R07。確認已保存的證據能依指定範圍交付，且內容與預覽一致。

**第五階段：原生驗收與收斂** — R09 → R10。完成平台矩陣、必要 UX 驗收、文件與 Issue 狀態更新。

#294 維持 Deferred；#344 等待新證據。它們不應阻擋目前核心功能收斂。

## 十四、完成後的目標狀態

REDLOG 不需要宣稱能攔截所有資安工具、所有網路流量或所有遠端操作。

它真正需要達成的是：

**使用者知道什麼已經被記錄、什麼沒有被記錄，以及已保存的內容是否能被可靠地搜尋、閱讀、關聯與驗證。**

因此，後續開發不應再以新增功能數量作為主要進度指標，而應以四個結果判斷：

1. **Capture Reliability：** 承諾的來源沒有未揭露的漏記或錯誤歸屬。
2. **Evidence Integrity：** 保存內容有可信版本及完整性邊界。
3. **Operational Usability：** 使用者能在實際平台完成接入、記錄、恢復與交付。
4. **Release Traceability：** 每項能力宣稱都有對應版本、測試及驗收證據。

在這四項完成之前，五個主工作區與 Reader 應以修復阻斷性問題為主，避免繼續投入大規模導覽改版。

**建議將 Spec 062 的剩餘流程驗收、Spec 064 的新工作區驗收，以及 #288–#296 的擷取要求統一納入這份收斂計畫，但仍由各自原有文件保有技術契約的唯一權威來源。**
